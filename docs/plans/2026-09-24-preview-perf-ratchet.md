# 预览性能 ratchet：先找能复现的数，再只许它往下走

长期约束（量什么、计数必须接满、比对规则、什么时候能重定基线、盲区）写在
[预览性能 ratchet](../architecture/preview-perf-ratchet.md)；本文记目标、拍过的板和探针实测。

## 一、目标（用户原话）

> 视频在预览的性能优化，我想你先找到可以量化复现的 benchmark，比如预览视频的时候消耗
> 更少的 CPU 指令数，然后做 ratchet …… 一旦某个 benchmark 的数值被优化到新低点（比如
> 某段代码从 100 条指令降到 52 条），就把这个新数值写进 CI 检查里作为新的上限。以后任何人
> 提交的代码，只要让这个数值超过 52，CI 就直接判定失败、拒绝合并。

没有具体觉得哪里慢，就是想一直往下优化；除了 CPU，GPU 之类别的可量化指数也可以加。

## 二、拍过的板（2026-09-24）

先讨论、列问题带推荐，用户逐条回复，其余「按你的建议」。推翻前先读理由。

| 决定 | 口径 | 理由 |
| --- | --- | --- |
| 在哪跑 | **只用 GitHub 托管的 runner**，不挂自托管 | 用户：自托管容易卡（机器睡眠、断网，PR 就一直排队）；公开仓库挂自托管 runner，别人从 fork 提的 PR 能在那台机器上跑代码 |
| 本地跑多少 | **少跑，只跑必要的**；测量全放 CI | 用户：本地跑发烫；公开仓库，CI 免费 |
| 量什么 | **数活**（body 重算、updateNSView、Canvas、建合成、开素材、换条目、建 tap）+ 合成负载代理数字 + 内存峰值；CPU 时间只报不卡 | 探针实测托管 runner 读不到指令计数器、CPU 时间差两倍（第三节）；讨论时就定了「读不到就走数活」 |
| 容差 | 计数**零容差**（两遍必须一样）；内存 10% | 用户同意要容差；计数是确定的整数，用不着；内存 runner 之间差 2–5%，首跑同一台上两遍也差 4% |
| 画质 | **不许拿画质换数字** | 用户拍板。按预览区尺寸合成、时钟降频都不算优化 |
| 新功能让数字合理上涨 | **只许降不许涨**：要加开销，得先在别处省回同样多 | 用户选的（两个选项里的第二个）。抬基线只留给不碰产品代码的「runner 环境变了 / 场景改了」 |
| 进步了没写进基线 | **判红** | 不然这次省下来的，下一个 PR 可以悄悄花回去 |
| 环境变了 | 单独开不碰产品代码的 PR，用「全部实测值」重定 | 讨论时想的是「在同一台机器上把 main 也量一遍当临时基线」，那是给有噪声的指令数准备的；改成数活之后数字基本不随机器变，没必要多编一遍 main |
| 放在哪一步 | CI 第 1 组单独一步，**不进 check-all.sh** | 要图形会话；第 1 组已经编好了完整 App |

## 三、探针实测

**本机**（M1 MacBook Pro，裸机，macOS 26.5.2；1080p 10 秒 H.264 解码 + 半尺寸半透明合成，跑 6 遍）：

| 指标 | 波动 |
| --- | --- |
| 本进程指令数（约 10.2 亿条） | 热跑之间差 0.6–1.8%；冷跑的第一遍多 15–29% |
| CPU 时间 | 差约 16% |
| CPU 周期数 | 差 25–56% |
| 能耗 | 差约 30% |

约 30% 的 CPU 花在 `VTDecoderXPCService` 里（不在本进程）；按进程统计的 GPU 时间读出来是 0。

**GitHub 托管 runner**（`macos-26`，三台同时跑；macOS 26.6.2 (25G83)、Xcode 26.6、
`VirtualMac2,1`、Apple M1 (Virtual)、3 核）：

| 项 | 结果 |
| --- | --- |
| 指令数 / 周期数 / 能耗 | **全是 0**（虚拟机没把硬件计数器给客户机） |
| 同一份 H.264 解码 + 合成的 CPU 时间 | 三台中位数约 670 / 400 / 310 ms —— **差两倍** |
| SwiftUI：200 次数据变化重算几次 | 三台、开窗口 / 不开窗口都**恰好 200** |
| 图形会话 | 有（`launchctl managername` = Aqua，屏幕 1024×768） |
| 真窗口里 `AVPlayerView` 播 4 秒 | 播了 3.93–4.00 秒，CPU 125–210 ms |
| 硬件解码 / Metal | H.264、HEVC、ProRes 都有；「Apple Paravirtual device」 |
| 自己的 Metal 活的 GPU 时间戳 | 三台 232–237 ms（很稳，但系统合成器的活看不到） |
| 内存峰值 | 同一段活三台差 2–5% |
| 同参数软件编码的素材 | 三台 sha256 一模一样 |

## 四、首跑（PR #67）

**第一轮就被「两遍必须一样」拦下了**：按 50ms 固定间隔跳时钟，两遍标尺重算 55 / 59 次，
电平表和音量线的 Canvas 跟着它多画少画（busy 连跳 Canvas 495 / 531）。原因是 CI 上 busy
场景一跳就要吃约 58ms CPU，比间隔还长，相邻两跳偶尔并进同一次屏幕刷新。改成每跳一下
都等界面停下来之后，第二轮两遍的每一项都一模一样（Canvas 正好 60 跳 × 9 个画布 = 540）。
「改几刀」那一段是一串异步的事，中间刷几次屏看时机，只卡事件计数，body / Canvas 只报。

代价：这一步在 CI 第 1 组要 2 分 9 秒（两个场景各两遍），整轮 CI 从约 2.5 分钟到约
3.75 分钟。

**第一份基线**（`macOS 26.6.2 (25G83) · Xcode 26.6 · VirtualMac2,1 · 3 CPU`）：

| 场景 | 时钟每跳一下 | 空闲 3 秒 | 改几刀 | 内存峰值 |
| --- | --- | --- | --- | --- |
| basic | 65 次 body、4 次 Canvas | 0 | 建合成 1、开素材 1、换条目 1、建 tap 1、快路径 1 | 128 MB |
| busy | 约 237 次 body、9 次 Canvas、22 次 `updateNSView` | 0 | 建合成 2、开素材 12、换条目 2、建 tap 6、快路径 1 | 285.7 MB |

合成负载：busy 全片 1136 层·帧、1983 百万像素·帧、滤镜 144 帧。

## 五、以后怎么优化：首跑看到的大头

每个优化单独一个 PR：改代码、看 CI 汇总页哪几项降了、把「改好的基线」写进
`baseline.json`。汇总页的「时钟跳 60 下每个视图重算了几次」按次数排好了序，从大头下手。

首跑 busy 场景时钟每跳一下（**画面上什么都没变**，播放器停着）：

| 谁 | 每跳几次 | 备注 |
| --- | ---: | --- |
| `InstantHelpModifier`（按钮的即时提示） | 152 | 占全部重算的 64%：每个带提示的按钮都跟着父视图重算 |
| `InspectorScrubbableNumberField` + 它的 `updateNSView` | 22 + 22 | 检查器里的数值框，值没变也每跳重来 |
| `ToolbarIcon`、`TransitionCard` | 各 11 | 工具栏图标、左栏转场库的卡片，和时间毫无关系 |
| `ClipBlockView` | 5 | 时间线上每个剪辑块 |
| 电平表、音量线的 Canvas | 各约 4 | 停着的时候也每跳重画 |
| `VideoEditView`（编辑器的根） | 1 | **根视图自己订阅了时钟**：每跳一下整个编辑器从根上重算，上面这些都是它带出来的 |

根上的那一条是源头：播放时时钟每秒跳 20 次，把检查器、素材库、工具栏全带着重算。

## 六、分刀（一个 PR，多个 commit）

1. 计数和测试入口：`PerfCounters`、全部视图插桩、`PreviewBench*`、扫描守卫。
2. CI：`scripts/check-preview-perf.sh`、比对器（带自检）、空基线、工作流。
3. 首跑抓到的不稳：每跳一下等界面停下来；「改几刀」只卡事件计数。
4. 第一份基线和文档。
