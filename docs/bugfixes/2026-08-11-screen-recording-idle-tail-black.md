# 录屏静止期不出帧 → 画面轨短于容器 → 进时间线后预览黑屏

日期：2026-08-11

## 症状

用 App 录屏，录完自动进主轨。**时间线上那一段是好的**（缩略图正常、时长
正常、能选中能拖动），**播放预览却是黑的**。用户报的那次是录一个窗口约
30 秒、只开电脑声音、没开麦克风，预览全黑；把那一段挪到画中画轨看着又「正常」了。

QuickTime 打开录屏文件一切正常 —— 所以第一反应会以为是编辑器的问题。

## 根因

### 画面轨的末端 ≠ 录制的末端

`ScreenCaptureKit` 在画面不变时只发**不带 image buffer 的 idle 帧**
（`ScreenRecordingWriter` 硬约束 6，占比实测可达 45–62%）。这些帧不写进文件，
只用来把 `observedEnd` 往前推。收尾时 `finish(stopHostTime:)` 用共同 T1 调
`endSession(atSourceTime: t1)`。

当年门槛 11 的结论是「`endSession` 足以把时长延到 T1，不需要补尾帧」——
**那次只验了容器时长**。真相是：

- **容器**时长确实被延到 T1；
- **画面轨**的末端仍停在「最后一次画面变化 + 一帧」。

`movieFragmentInterval = 1s` 还让这件事无法自愈：最后那份画面采样早就被冲进
某个 fragment、时长已经定死，`endSession` 再也改不动它。
（没有第二条轨在写的时候反而不会暴露 —— writer 还没冲 fragment，收尾时最后
一帧还能被延长。所以**必须有电脑声音这一路**才复现，自检里踩过这个坑。）

实测用户自己的录屏 `Screen Recording 2026-08-08 10.29.24.mov`：

| 量 | 值 |
| --- | --- |
| 画面轨 `timeRange` | 0 → **9.56s** |
| `AVURLAsset.duration`（= `MediaProbe` 拿到的时长） | **10.676s** |
| 音频轨 | 0 → 10.68s |

### 为什么播放器看不出来、编辑器却全黑

播放器把最后一帧**冻在屏幕上**播到容器末端，肉眼看不出画面轨提前结束了。

而 `VideoEditCompositionBuilder.insert` 是按**画面轨真实存在的范围**取材的
（`available = trackEnd - start`，这是对的：越界会抛错，音频轨常比视频短一截）。
剪辑块在时间线上的长度却来自 `MediaProbe` 的 `asset.duration`。两者差多少，
预览里就有多少**纯黑**：

```
[单段主轨 + 那个文件] luma 0.2:0.88 … 9.2:0.88 10.2:0.00
                                                    ↑ 画面轨 9.56s 之后
```

差值 = **停止录制之前，画面静止了多久**。用户那次录的是一个窗口：窗口内容不变
的那段时间里一帧都没写，所以黑掉的是绝大部分，看起来就是「整段全黑」。
挪到画中画轨并不能修好它（那条路径同样调 `insert`）——「挪过去就好了」
应当是当时播放头正好停在开头有画面的位置。

## 修复

`ScreenRecordingWriter`：新增硬约束 7「**画面轨必须自己盖到 T1**」。

- `appendVideo` 成功写入后留住最后一份 image buffer 与它的 format
  （代价是一块 IOSurface）。
- 新增 `holdLastFrame(untilT1:)`，在 `markAsFinished` **之前**调用：画面轨末端
  距 T1 还差半帧以上时，把最后一帧再写一份，PTS 接在上一份之后（严格单调，
  否则 writer 直接判 failed），duration 铺满到 T1。等待编码器就绪是**有界**的
  （1 秒上限 + 查 writer 状态），宁可少这一帧也不让退出卡死。
- 一帧都没写过（画面轨本来就空）时不动作，如实回报原因。

**补尾帧失败不许静默**（复审 P1）。`holdLastFrame` 的每一条提前退出都返回原因，
但判 partial 不拿它当判据 —— 而是收尾后**打开写好的文件**读画面轨真实的
`timeRange.end`，比 T1 短半帧以上就判 partial（文案：录制尾部没有画面）。
理由是「外部真值」：内部账只能说明「我以为写进去了多少」，补帧失败之后
writer 照样可能是 `.completed`，只看容器时长和音频覆盖，短画面轨会被当成功
提交、黑尾原样再来一次。`FinishResult` 同时带出 `videoTrackEndSeconds` 和
`tailFrameFailure` 供诊断。

同时订正文件头硬约束 5 里那句过期结论（「不需要补尾帧」），并在
[实施报告结论 B](../reports/2026-08-06-native-screen-recording-implementation-report.md)
上标注**已推翻**：当年只量了容器 Duration，没有逐轨量 `AVAssetTrack.timeRange`。

## 验证

新增 `scripts/check-screen-recording-writer.sh` +
`checks/ScreenRecordingWriter/main.swift`：用真实 writer 喂 1 秒真画面 + 4 秒
idle 帧（电脑声音全程在写），落文件、建预览合成、量像素。

- **反向验证做了两轮，第一轮的守卫根本红不了**，记在这里免得下次重犯：
  1. 假 PTS 几毫秒喂完 6 秒 → 所有采样落在同一个 fragment，收尾时最后一帧还能
     被延长 → 7/7 全绿。必须**按真实时间**喂。
  2. 没有电脑声音那一路 → 静止期没有任何轨在写，同样不冲 fragment → 又是全绿。
     必须同时喂音频。
- 两条都补上之后，撤掉修复实测红：画面轨 **1.48s** vs 录制 **7.47s**，
  预览 2.5s 与 4.5s 处亮度 **0.00**；恢复修复后全绿
  （画面轨 7.437 = 容器 7.437 = 录制 7.436）。
- 复审后守卫加严到 15 条，再做一次反向验证：除上述四条外，
  **「不该被判 partial」也如期变红**（`The end of the recording has no picture…`）
  —— 证明产物验收这道闸真的会拦住短画面轨。守卫同时断言场景前提本身成立：
  idle 帧 > 90、画面只写了头 1 秒那些帧、电脑声音全程写入（≥100 包）、
  产物里确有音轨且覆盖大半段。**造不出静音采样直接让检查失败**，
  不再 `if let` 静默跳过 —— 那等于把「没有第二条轨」那种不出问题的情形悄悄
  换上来，守卫从此永远绿。
- 真机端到端：用真实 `ScreenCaptureEngine` + 修复后的 writer 录 10 秒窗口，
  画面轨 0→10.5367 与录制时长一致，`written` 未多写多余帧（无洞时
  `holdLastFrame` 是 no-op），预览逐点亮度 0.95 无黑帧。
- 全量 `scripts/check-all.sh` 通过。

## 教训

- **「容器时长对了」不等于「画面轨对了」。** 验收产物必须逐轨看
  `AVAssetTrack.timeRange`，别只看 `asset.duration` —— 播放器会用「冻住最后
  一帧」把这个差别藏起来，只有进合成才会现原形。
- **`endSession` 不是补帧。** 它只延时长；分片写入下连最后一帧的时长都改不动。
- **变帧率产物的隐式合同**：「画面轨覆盖整段时长」是下游（`insertTimeRange`、
  导出、缩略图）默认成立的前提。生产端要保证它，消费端 `insert` 的收口逻辑
  没有错，不要去改那里。
- **自检要连"触发条件"一起复刻**：这次真正的触发条件是 fragment 已冲出去
  （＝真实时间 + 另一条轨在持续写）。少一个条件，守卫就是绿的，等于没写。
  推论：**触发条件本身要写成断言**（idle 帧数、音频包数、产物有音轨），
  否则环境一变，守卫会安静地退化成测了个不相干的场景。
- **收尾路径上的「尽力而为」必须留下痕迹。** 补尾帧是尽力而为的（编码器可能
  不收），但失败后不能静默 return —— 收尾之后要拿**产物**再验一遍，
  验不过就判 partial。这是仓库既有的「外部真值」纪律
  （见 [录屏地基复审](2026-08-07-screen-recording-foundation-review.md)）在
  产物验收上的又一次应用。
