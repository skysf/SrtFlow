# 2026-09-29 text_scan 的字幕行：被切掉的字混进来、字幕稀疏时选成了幻灯片

## 症状

PR #81 合并后交接里留了 text_scan 的三个「潜在弱点」，都是复查 L27 时看逐帧数据发现、当时没修：

- (a) `captionLike` 只认高度 ≤ 0.12，L27 151 秒那帧 0.141 高的框被漏掉，疑似「两行字幕被 Vision 合成一个框」；
- (b) 底边容差 0.02 让贴着画面底边被切掉的字（L27 的 PDF 最后一行，底边 0.997）混进字幕行；
- (c) 上沿取 10% 分位，框只有十来个时基本等于最小值，一个错认就够。

没有出错的画面（六节课的裁切量都对），但 L27 的字幕带框是 y 0.883–**0.997**、x 0.14–0.83：底边被抬到画面边缘，x 比真字幕宽一大截。
`look text_scan` 的框以后还要给「盖一块」（模糊 / 马赛克，方案第 56 条）当位置，脏框不能留。

## 根因

拿六节课（调参用的）+ 七节没参与调参的课（L17、L19、L21、L22、L23、L24、L25）逐帧打出下面三成的字框，在 Python 原型和 Swift 重放里前后对比，
查出来三件事，**只有前两件是真的**：

1. **(b) 是真的，而且比想的重**。L27 生产抽样（24 帧）里，被选进「字幕行」的 9 个框只有 4 个是字幕（含汉字的占 44%），另 5 个是 PDF 页
   往下滚出画面时只露出一道的那一行（框底边 0.997、高 0.011–0.028，字一直在变：`and mationa`、`avtro limhe…`）。它们每帧不同，
   「不同的字最多」这条规则偏袒它们；字幕的底边（0.975–0.978）恰好落在它们 0.02 以内，才被一起收进来，看起来没出事。
   录屏里滚动的页面、文档几乎都有这一行。
2. **选行规则本来就靠运气**。光把截断字滤掉（第一版修法）L27 反而更糟：字幕带跑到 0.762–0.836、要裁 0.25。因为这节课字幕稀疏（24 帧里 4 帧有），
   幻灯片在 0.80–0.84 一小段里有 7 句不同的字（每页停两帧），「不同的字最多」选了幻灯片；修之前是截断字碰巧凑了数。
3. **(a) 的前提不成立**：把 151.5 秒、153.0 秒两帧抽出来看，字幕是**一整行**（「在下一个视频中，我们将讨论钱的问题。」，字形 0.90–0.965），
   那个 0.860–1.001 的框是 Vision 在花背景上把一行字的框量大了，不是两行合并。六节课近 300 帧有字幕的画面里，没有一处真的两行合并成一个框（唯一一处
   「上下叠着两个汉字框」是幻灯片上的一个字）。所以上限 0.12 在这一帧上**是对的**：放宽了会多裁 0.04。
4. **(c) 没有真实的样本**：上沿的分位数偏向最小值确实是事实，但六 + 七节课里没有第二处错认（第一处「幻灯片标题被当成上一行」已在
   [裁切量被幻灯片标题拉大](2026-09-29-text-scan-crop-hint-stretched-by-slide-title.md) 修掉）。「丢掉最极端的那个」会同时丢掉真的少见的两行字幕，
   两头都只是推测，不改。

## 修复

`Sources/SrtFlow/AITextRegions.swift`：

1. `captionLike` 加 `cutOffAtBottom`：框底边到了 0.99 以下的画面边缘、高又不到 0.04（一行字幕至少这么高）的，是被画面底边切掉的字，不算字幕行。
   真的字幕离底边总留着空（六节课底边 0.95–0.98），整行高的字幕哪怕贴着边（底边 0.995、高 0.06）照旧认。
2. `subtitleLines`：字幕是**够多的几堆里最下面的一堆**，不再是「不同的字最多」。够多 = 至少 3 句不同的话、也至少是最多那一堆的三分之一
   （`minSubtitleTexts`、`rowShare`）；选定后以这一堆底边的中位数为中心再收一遍（只看候选上面 0.02 以内会收掉半堆）；没有一堆够格就是没有字幕带
   （`band()` 里空就返回 nil）。理由：字幕排在画面最下面，它下面再有的东西不是被切掉的字（第 1 条滤掉）就是台标、页脚，撑不起三句；
   幻灯片的字再多，也是在字幕上面。
3. (a)(c) 不改，把判断写进了 `captionLike` 的注释。

## 验证

- **裁切量前后一样**（`look text_scan` 提示的 `crop bottom`，生产抽样 24 帧 + 每 2–3 秒一帧的密集抽样，共 26 组）：六节课 0.11 / 0.11 / 0.11 / 0.13（L27）/
  0.12（L28）/ 0.11；留出的七节课 0.11 / 0.11 / 0.11 / 0.11 / 0.11 / 0.12 / 0.12。没有一组变。
- **变了的只有脏边**：L27 框的底边 0.997 → 0.978（生产抽样，字幕行 9 个框 → 4 个、全是字幕）/ 0.997 → 0.980（密集抽样，含汉字的占 54% → 96%）；L17 密集抽样底边 0.971 → 0.967。
- `checks/MCP/TextScanChecks.swift` 加了八条（`scripts/check-mcp.sh` 里的第 24 项）：
  贴底的截断字在字幕远处 / 近处各一条、整行高的贴边字幕照认、一行字幕被量成 0.141 高的框不拉大字幕带、字幕稀疏而幻灯片字多、
  下面三句的页脚抢不走字幕带、两句轮着出现不是字幕。
  **反向验证**：整个换回修复前的 `AITextRegions.swift`，四条红（框成 0.983–0.997、提示裁 0.03、底边 0.997、稀疏那条框成 0.78–0.834 选了幻灯片）；
  只去掉「三分之一」的门槛（`rowShare` 改成 1000），页脚那条红；恢复后 41 条全过。其余几条（贴边整行字幕、过高的框、两句轮换）前后都绿，
  是这次设计的边界钉子，不是修复的证据。
- 本机小工具（scratchpad，重启就没了）：`replay`（读 ts2 打出的逐帧字框，喂给生产的 `AITextRegions.report`）、Python 原型；逐帧数据用 ts2 探针认出来。

## 教训 / 防回归

- **「谁最多」在样本稀疏时不可靠**：这条规则在字幕密集的 12 节课上一直对，是因为字幕碰巧最多；L27 的字幕只占 24 帧里的 4 帧，被别的东西的数量盖过去。
  选规则要用**位置上的先验**（字幕是最下面的一行）加一个最低的支撑，而不是只比数量。
- **修掉一个脏数据源之前，先看它是不是在替别的毛病挡枪**：截断字滤掉之后 L27 更糟了，才看出选行规则的毛病；拿另一批没调过参的素材（留出集）前后对一遍，才敢说没退步。
- **对一个交接里的「猜测」先核对再动手**：(a) 的说法是上个会话对着数字猜的，抽两帧出来看一眼就推翻了；写进案例，免得下次又有人去放宽 `captionLike`。
