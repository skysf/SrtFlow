# 2026-09-30 成片的声音过了 0 dBFS 交给 AAC：峰值 +2 dBFS、主推子降 3 dB 成片只降 2 dB

## 症状

用户用 MCP 剪婚礼视频（报告 BUG-08）：A1 音乐 −2 dB，A2–A4 上 17 个音效各 −2 到 +5 dB。主音量 0 dB 导出，成片整体峰值
**+2.15 dBFS**，没有任何提示；主音量 −3 dB 再导，每 100 ms 窗的 RMS 该一律低 3 dB，只有音乐的地方正好 3.0，
有音效叠加的地方只低 1.3–2.5 dB；0.42 秒处主音量 0 时 −2.04 dBFS、−3 时反而 +0.12。用户怀疑混音里有没说明的限幅、压缩。

## 根因

同一工程拷出来照做（主推子 0 / −3 各导一次），数字和用户量的一样（峰值 +2.15 / +0.12，RMS −10.09 / −12.93，
165 个窗里 30 个降幅不到 3 dB，最少 0.74）。然后拿自检的地基写探针：0.9 满幅的正弦两轨各 +6 dB 叠加 ——

| | 混音（AVFoundation 读出来的 float） | 成片（AAC 解回来） |
| --- | --- | --- |
| 主推子 1.0 | 峰值 +11.35 dBFS、RMS +8.11 dB | 峰值 +12.18 dBFS、RMS **+3.57** dB |
| 主推子 0.708（−3 dB） | 峰值 +8.35、RMS +5.11（**正好差 3.00**） | 峰值 +8.87、RMS +1.57（差 **2.00**） |

（探针按单声道混下来读，两声道各自的数低 3 dB；相对关系不变。导出那条路读的是立体声，同一段混音封顶前的峰值记成 +8.3 dBFS。）

**混音本身是线性的、不削**（单轨 +12 dB 读出来正好 +11.3 dBFS，主推子一分不差）；`AVAssetReaderAudioMixOutput` 读的是 f32，
和过 0 照样写进中间文件。**问题在 AAC 编码器**：喂给它超过 0 dBFS 的信号，成片 RMS 掉 4.5 dB、峰值却冒到 +12 dBFS，
掉多少随电平变 —— 所以主推子在成片里不再线性，只有音乐（没过 0）的地方才正好 3 dB。播放器解码再削一次，
用户听到的是两重失真。

## 修复

`ExportAudioMixdown`（`VideoEditExportMixdown.swift`）：写 f32 时**每个采样在 −1 dBFS 封顶**（`peakCeiling` = 0.891，留 1 dB 给
编码器的过冲，和配音文件同一个口径），**封顶前的峰值和削了多少帧记在 `Levels` 里**；`Outcome.written(Levels)` 带出去，
`VideoEditExportGraph.Plan.audioLevels`（`Plan` 顺手拆成 `VideoEditExportPlan.swift`，导出图那个文件只许降）→ `VideoEditExporter.finishedAudioLevels`。

告诉用户：导出面板成品那一行下面一句橙字「声音峰值 +2.1 dBFS：有 0.35 秒被削到 −1 dBFS。把主音量至少降 3.1 dB。」；
AI 的 `get_job` 结果带 `audio_peak_dbfs`，削了的还带 `audio_clipped_seconds` 和 `note`（叫它 `set_track master volume_db` 压下去再导）。
不做限幅器、不做响度目标（用户要的选项，另拍板）。

## 验证

- `scripts/check-audio-fade.sh` 第 10 组（`checks/AudioFade/Ceiling.swift`）：0.9 满幅正弦两轨各 +6 dB 真跑导出 ——
  封顶前的峰值记成约 +11 dBFS、削了的时长照实、f32 里没有一个采样超过 −1 dBFS 且最响处正好贴着它、成片解回来的峰值不冒出 0、
  成片响度和混音差不到 0.5 dB（封顶前差 4.5）；主推子压到 0.2 之后一帧不削、峰值按线性算。
  **反向验证**：把 `peakCeiling` 临时改成 1000（不封顶），第 10 组红（f32 里有采样超过 −1 dBFS、成片峰值冒出 0、成片响度和混音对不上）；改回来全绿。
- 一条轨的峰值当尺子、两轨叠加按线性比（4 倍），不写死绝对值：素材经 AAC 一来一回、读法的口径都在尺子里。

## 教训

- **两份结果互相比之前，先把每一级单独量一遍**：混音和成片各量一次，一眼看出线性的是哪一级、不线性的是哪一级；
  只看成片会把编码器的账记到混音头上（用户怀疑的限幅、压缩其实都不存在）。
- **有损编码器不是透明的管子**：过 0 dBFS 的 float 它收下不报错，出来的东西和电平有关。给它的东西自己先封顶、把封顶前的数报出去。
- 一句「过 0 了」的提示比默默削更重要：用户自己量出来才发现，说明该在结果里说的没说。
