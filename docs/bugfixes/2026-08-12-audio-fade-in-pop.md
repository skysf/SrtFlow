# 2026-08-12 渐入开头「砰」的一下：混音器把 1.0→0 的增益跳变平滑进了渐入

## 症状

给音频段设了渐入之后，**预览播放**时渐入的最开头有一下很短促的大音量，
然后才正常渐入。用户描述：「渐入音频开始那一点点没有 apply 渐入」。

导出的成品没有这个问题。段**从时间线 0 开始**时也没有 —— 这是它躲过首轮
自检的原因。

## 根因

不是渐入没生效，是**多了一条从满音量降到 0 的下坡**贴在渐入最前面。

按毫秒量出来的形状说明了一切（段起点后每毫秒峰值，素材满幅是 0.125）：

```
0:0.121  1:0.113  2:0.106  …  16:0.009  17:0.002  18:0.001 …
```

一条从满音量线性降到 0 的斜坡，长约 17ms，正好是一个音频处理缓冲区。

`AVMutableAudioMixInputParameters` 的语义：**第一条斜坡之前的音量默认是
1.0**。渐入斜坡的起点值是 0，于是在段起点处存在一个 1.0 → 0 的跳变，而
AVFoundation 的混音器不会硬切增益，它会把跳变按一个缓冲区平滑过去
（de-zipper）。结果就是渐入的头 17ms 变成「满音量 → 0」的下坡，听感是
「砰」一下再渐入。

为什么段从 0 开始时没有：那时斜坡起点就是合成的起点，**前面没有可跳变的
区间**，混音器直接从 0 起步。

为什么导出没有：ffmpeg 的 `afade` 是逐样本算增益的，不存在跨缓冲区的
de-zipper。**两条管线在这一点上语义不同 —— 这正是必须两条都真跑一遍的理由。**

### 为什么首轮的守卫没抓到（这条最值得记）

`scripts/check-audio-fade.sh` 首轮就是「真跑两条管线量包络」的检查，
它照样放过了这个 bug，两个原因叠在一起：

1. **所有用例的段都从时间线 0 开始** —— 恰好是唯一不触发跳变的位置。
2. **断言看的是 100ms 窗口的 RMS** —— 2ms 的满幅爆音只把 100ms 的 RMS 抬到
   0.14，17ms 的下坡抬到约 0.17，而阈值是 0.15，**擦着边过**。

「真跑生产路径」不等于「测到位」：**场景选在了默认值上，量纲选得比缺陷粗**，
再真实的管线也照样绿。

## 修复

`VideoEditCompositionBuilder.addVolumeRamps`：在段起点**之前一个平滑窗口**
就把音量钉住，让跳变发生在段起点前的静音空档里。

```swift
let pin = max(previousEnd, clip.timelineStart - gainSmoothingGuard)  // 50ms
params.setVolume(fadeIn == nil ? volume : 0, at: time(min(pin, clip.timelineStart)))
```

三个细节：

- **钉的值分两种**：有渐入的钉 0，没渐入的钉 body 音量本身。一律钉 0 的话，
  所有不从 0 开始的段都会被 de-zipper 加上一个 17ms 的软起音 —— 修一个 bug
  造一个新的。自检里有反例对照钉着这一条。
- **不能越过上一段**：`previousEnd` 是同一条合成轨上上一段的结束点，钉点
  夹在它后面，否则会啃掉上一段的尾巴。三个调用点都要在 `insert` **之前**
  抓游标（插完游标就被推到本段末尾了）。
- 主轨的声音走 A/B 交替两条轨，各有自己的 params 和游标，`previousEnd`
  取的是**同一条轨**上的上一段，不是时间线上的上一段。

## 验证

- `scripts/check-audio-fade.sh` 新增第 4 组：段从 **1.3337s** 起（非 0、
  且不在 600 时基整格上）、看**峰值**而不是 RMS，预览与导出各一条；
  外加「同位置不设渐入」的反例对照（防止修复给所有段加软起音）。53 项通过。
- **反向验证**：把 `params.setVolume(...)` 那行换成 `_ = pin`，新守卫当场变红
  （`head/full=0.96`），恢复后转绿。
- 首轮的三次反向验证（导出 afade、预览斜坡、转场仲裁）重跑仍然有效。
- `scripts/check-all.sh` 全绿。

# 第二轮：50ms 是个赌注，而离线自检永远赌赢

第一轮修完、53 项自检全绿、`check-all.sh` 全绿，用户当天下午仍然报同一个症状：

> 我加入了一个 BG2 音乐，开头有一个不属于这个音频文件的、类似于爆的音，很短促。
> 如果我不降低音量不那么明显，一旦降低音量就这样。同样的文件在剪映里没有。
> 按道理降低音量又开了 3 秒 fade in，最初应该没什么声音，但还能听到那个短促的声音。

## 用户描述里最值钱的一句

「**降低音量反而更明显**」。这句话直接锁死了根因的形状：

- 如果爆音在素材里 → 它会跟着音量一起降，相对响度不变，不可能「更明显」。
- 如果爆音走了音量/渐变这条链 → 3 秒渐入在开头把增益压到 0.001 量级，
  任何东西都会被压到 −50 dB 以下，听不见。

**唯一能同时满足两条的，是一段「不经过用户音量、从 1.0 起步」的增益。**
这正是 de-zipper 的形状 —— 也就是第一轮认定并「修好」了的那个东西。

## 根因：提前量必须大于渲染缓冲区，而缓冲区大小随播放路径变

第一轮把提前量定成常量 50ms，依据是「实测跨越跳变的那个缓冲区约 17ms」。
问题在于**那个 17ms 是在离线管线上测的**：

| 播放路径 | 谁在用 | 渲染缓冲区 |
| --- | --- | --- |
| `AVAssetReaderAudioMixOutput` | 自检、导出前的量取 | ~17ms |
| `AVPlayer` 实时播放 | **用户听到的预览** | 可到 ~90ms（4096 帧 @44.1kHz）|

50ms 覆盖得住 17ms，覆盖不住 90ms。于是：

- 自检里钉点提前 50ms，跳变在段起点前就滑完了 → **全绿**。
- 真实预览里跳变还没滑完，段起点已经到了 → 渐入最前面仍然贴着一条
  从 1.0 滑下来的坡 → **「砰」**。

而这条坡从 **1.0** 起步，跟用户设的音量毫无关系：音量调得越低，音乐被压得越轻，
这条坡就越突出。用户的「降低音量反而更明显」就是它。

BG2 这个素材还叠了一层不巧：文件开头有约 39ms 的静音，音乐在 39.4ms 处
**硬起**（单样本跳变 9658，≈ −5 dBFS）。滑坡的残余增益正好落在这个硬起上。

### 为什么离线自检不可能抓到它

这一轮最该记的一条：**第一轮的自检方法论本身有个天花板**。

「真跑两条管线量 PCM 包络」听起来无懈可击，但自检跑得到的那条管线
（`AVAssetReader`）**和用户听的那条（`AVPlayer`）缓冲区不是一个量级**。
任何「提前量 = 常量」的修复，都能在自检里绿、在真机上响。
**再怎么加用例、再怎么把 RMS 换成峰值，都突破不了这个天花板** —— 因为
自检压根跑不出 AVPlayer 的缓冲区。

## 修复：不再赌缓冲区，把钉点退到「上一段结束处」

`VideoEditCompositionBuilder.addVolumeRamps`：

```swift
// 旧：赌缓冲区 ≤ 50ms
let pin = max(previousEnd, clip.timelineStart - gainSmoothingGuard)
// 新：钉到同一条合成轨上上一段结束的地方（首段即 0）
let pin = min(previousEnd, clip.timelineStart)
```

依据是一条与缓冲区长度**无关**的事实：同一条合成轨上，上一段结束到本段起点
之间**全是空段（静音）**，钉多早都碰不到别人的声音。于是跳变爱平滑多久平滑
多久，都发生在静音里。一条轨的第一段钉在 0 —— **每条合成轨从第一帧起就有
确定的音量，再也不会撞上 AVFoundation 的默认 1.0**。

`gainSmoothingGuard` 这个常量一并删掉：它代表的那个「我知道缓冲区多长」的
假设本身就是错的，留着迟早有人再去调它的数值。

顺带收进来的同类问题：**静音段**以前走的是单独分支
`params.setVolume(0, at: 段起点)` —— 钉在起点上，等于把 1.0 → 0 的跳变留在段内，
静音段开头照样会漏出一下声音。现在它和其它段走同一条路（`addVolumeRamps`
里的音量本来就是 `isMuted ? 0 : volume`）。

## 验证

把断言从「量包络」换成**结构不变量**，这样才不依赖任何缓冲区长度：

> 每条合成音轨的**第一个音量设定点必须落在时间 0**。
> 换句话说：没有任何一条轨会用到 AVFoundation 的默认 1.0。

用公开 API `AVMutableAudioMixInputParameters.getVolumeRamp(for:...)` 读回来断言。
注意它的语义有个坑：**查询点早于第一个设定点时它照样返回 `true`**，把后面那条
斜坡连同起点一起给出来（`range = [1.2833, inf]`）。所以判据不能看返回值，
要看**第一条斜坡的起点**落在哪。

- `checks/AudioFade/main.swift` 新增第 4b 组，5 个场景：偏移段有/无渐入、
  用户真实形态（背景乐在 **24.39s** 起、音量 0.12、渐入 3s）、静音段，
  以及**主轨接缝**（声音走 A/B 交替两条合成轨，钉点很可能只错一条）。
  70 项通过（原 53）。
- **反向验证**：把钉点换回 `max(previousEnd, start - 0.05)`，
  4 条当场变红并打印出「第一个设定点在 1.2833s / 24.3417s」；恢复后转绿。
- `scripts/check-all.sh` 17 组全绿；该脚本已挂在
  `.github/workflows/checks.yml` 上，每个 PR 和推 main 都会跑。
- **真实预览由用户听感确认**（0.9.0-dev.audiopop 构建，2026-08-12）：
  BG2 低音量 + 3 秒渐入，开头的爆音消失。离线自检在原理上无法替代这一步 ——
  见上「为什么离线自检不可能抓到它」。

## 教训 / 防回归

1. **音频瞬态要用峰值量，不能用 RMS。** RMS 的窗口越大，越会把几毫秒的爆音
   摊平到阈值以下。抓 click/pop 一律看窗口内峰值。
2. **自检的场景不能全落在默认值上。** 段起点、素材偏移、变速这些参数，至少
   要有一组**故意选在非零、非整格**的值上。这个 bug 的全部特征就是
   「timelineStart ≠ 0」。
3. **预览（AVFoundation）和导出（ffmpeg）在增益语义上不等价**：前者有跨缓冲区
   的 de-zipper，后者逐样本。任何「设一个增益曲线」的功能，两条管线都得真跑。
4. 长期约束已落到
   [architecture/audio-fades.md](../architecture/audio-fades.md) 的
   「斜坡之前必须先钉音量」一节。

以下三条来自第二轮，比上面四条更根本：

5. **不许用「常量提前量」去躲平台的平滑窗口。** 窗口长度是平台实现细节，
   还随播放路径变（离线 ~17ms / 实时 ~90ms）。要么把动作放到**语义上安全**
   的位置（这里是「上一段结束处」——那之后全是静音，与窗口长度无关），
   要么就别做。任何 `= 0.05` 这样的数字都是在赌一个你没量过的量。
6. **自检能跑的管线 ≠ 用户听的管线。** 音量/渐变的最终裁判是 `AVPlayer`，
   而自检只够得着 `AVAssetReader`。碰到这种天花板，断言要从「量输出」
   上移到「**查结构不变量**」—— 不变量对两条路径同时成立，输出不成立。
7. **用户描述里的「反常关系」是最强的线索**，比「有没有 bug」值钱得多。
   「降低音量反而更明显」一句就排除了「爆音在素材里」和「爆音走了增益链」
   两大类，只剩「有一段增益不经过用户音量」——直接指到根因。
   听到这种反常关系，先去解释它，别急着复现。
