# 2026-08-08 图片进时间线还是慢：`-loop 1` 让同一张图被解了 120 次

> 同一天早些时候已经修过一次这条命令
> （[输入帧率](2026-08-08-still-clip-loop-decode-slow.md)，1500 次解码 → 120 次），
> 这次是把剩下的 120 次也干掉：**一次**。

## 症状

用户报的：「把图片添加到轨道，如果图片比较大，比如 5MB 左右，加载缓慢，在播放的
时候，预览窗口是黑屏，图片加载应该是秒级的。」

复现（本机 M1、5.4MB / 4200×3150 PNG、清空静帧缓存、真实窗口）：
预览区一直是黑的，**到第 5 秒**才出画面。期间时间线上是占位块（预览合成会跳过
它，见 `VideoEditCompositionBuilder`），所以看着就是黑屏。

## 根因

上一次修完之后命令是这样的：

```
ffmpeg -loop 1 -framerate 2 -i x.png -t 60 -r 2 -vf scale=... -c:v libx264 ...
```

`-framerate 2` 把 demuxer 的吐帧速率对齐到了输出，解码次数从 1500 降到 120。
但**120 次仍然全是重复劳动**：`-loop 1` 的语义就是「让 demuxer 一遍遍重新吐这张
图」，于是每一个输出帧都要**重新解一次 PNG/JPEG、重新缩放一次**。画面是死的，
这 120 次解码里有 119 次的结果与第一次完全一样。

图越大越贵 —— 这就是「5MB 左右就明显慢」的原因：耗时几乎全在解码，与输出的
1080p 120 帧无关。

实测（本机 M1，`vendor/ffmpeg` 8.1，照片政策 → 1440×1080 / 120 帧）：

| 素材 | 修前 | 修后 |
|---|---|---|
| 4000×3000 PNG（4.7MB） | 4.8s | **0.37s** |
| 4200×3150 PNG（5.4MB） | ~5s（真实窗口口径） | **~0.5s** |
| 6000×4500 PNG（9.5MB） | 8.8s | **0.63s** |
| 6000×4500 JPEG（2.5MB） | 7.1s | **0.32s** |
| 3840×2160 PNG（定格政策，原尺寸输出） | 3.4s | **1.3s** |

## 修复

`Sources/SrtFlow/StillImageClipFactory.swift`：**只解一帧，其余 119 帧用 `loop`
滤镜复制**。

```
ffmpeg -r 2 -i x.png -vf "scale=...,loop=loop=119:size=1:start=0" \
       -frames:v 120 -r 2 -c:v libx264 ...
```

三处改动，各有各的必须：

1. **`-vf ...,loop=loop=119:size=1:start=0`** —— 缩放也只做一次（`loop` 在缩放
   之后），复制的是**已经缩好的**那一帧。
2. **`-frames:v 120` 取代 `-t 60`** —— `loop` 复制完之后会把输入**剩下的帧**接着
   往下吐。单帧图片没有剩下的帧，但动图 gif/webp、多页 tif 有：不截断的话产物是
   129 帧 / 64.5s，图片段的可拖长度就跟着错。帧数是这条命令里唯一确定的量，
   拿它当上限最省事。
3. **`-r 2` 取代 `-framerate 2`（输入侧）** —— 见下面「顺带修好的」。

产物**逐字节相同**（PNG / JPEG 两条政策各对过 md5），所以缓存版本号**故意没升**：
升了只会让所有人白重转一遍。

### 顺带修好的：gif 和 heic 以前根本进不来

`-loop` 和 `-framerate` 都**只有 image2 demuxer 有**。`.gif` 走 gif demuxer、
`.heic` 走 mov demuxer，两个都会在开文件那一步就死：

```
Option loop not found.
Error opening input file anim.gif.
```

而 `MediaFileTypes.isImage` 一直把 `gif`/`heic`/`heif` 算作可以拖上时间线的图片，
所以这两类文件拖进来必然弹「Could not use X as a clip.」。换成通用的 `-r` 之后
gif 和单图 heic 都正常了（gif 取第一帧当静帧 —— 静帧管线本来就只有一帧的语义）。

**仍然不支持**：tile grid 型 heic（iPhone 大图常见，探测时显示
`Stream group #0:0 ... Tile Grid`）。ffmpeg 要用内部的 complex filtergraph 把
瓦片拼起来，于是 `-vf` 用不了，报「Simple and complex filtering cannot be used
together」。**别顺手改成 `-filter_complex "[0:v]..."` 糊过去**：`[0:v]` 选中的是
**单块瓦片**，4000×3000 的图会静默变成 512×512 —— 从「明确报错」退化成「悄悄给
错画面」。要支持得走 `[0:g:0]`（stream group），但它在普通 png 上会报
「matches no streams」，也就是必须先分辨输入是不是 tile grid，属于另一件事。

### 性能断言怎么写才不飘

这类 bug **产物完全正确**，只看文件永远发现不了 —— 必须有一条对着时间的断言。
但绝对秒数跨机器不成立，「全程/单帧」的比值也不够：反向验证里那个比值只有
6.6×，而正确实现自己就能到 5.8×（原生政策要编 120 帧原尺寸）。

最后用的判据是**边际成本**：

```
基线 = 生产参数只出 1 帧   ≈ 起进程 + 解一次图 + 缩一次 + 编 1 帧
全程 = 生产参数出满 120 帧
断言：全程 - 基线 ≤ 基线 + 0.25s      （多出来那 119 帧，不许贵过一次解码）
```

图只解一次时那 119 帧只是编码 1080p，边际成本远小于一次解码；逐帧重解的话边际
成本就是 119 次解码，必然几倍于一次。两边都随机器一起缩放，不用写死秒数。
本机实测：解一次 delta=0.18s / 上限 0.67s（余 3.7×）；逐帧重解 delta=6.64s /
上限 1.22s（超 5.4×）。素材要够大（自检里用 6000×4500）——解码成本必须明显
大于「编 120 帧 1080p」，否则分不出好坏；也只量照片政策，原生政策的编码本身就
占大头。

基线是从**生产参数数组里改出来**的（找到 `-frames:v` 换成 `1`），不是另写一条
命令：另写一条的话生产参数改了、基线还照着老路子跑。

## 教训 / 防回归

- **`-loop 1` 不是「把这一帧留住」，是「把整个输入重放一遍」**。要静止画面，
  正确的说法是「解一帧 + `loop` 滤镜复制」；`-loop` 只适合真的想重放输入的场合。
  上一次修只把重放的**次数**对齐了，没质疑重放本身 —— 同一个假设被修了两次。
- **同一条命令的性能 bug 会连着来**：第一次量出 19.4s→2.2s 就收工了，没有人问
  「2.2s 里还有多少是白干的」。**修完性能问题要再量一次边际**。
- **demuxer 私有选项会静默吃掉整类格式**。`-loop`/`-framerate` 是 image2 专属，
  写进通用命令后 gif/heic 全灭，而错误信息是「Option loop not found」，
  跟图片一点关系都看不出来。给「所有图片」用的命令只能用通用选项。
- **别用 `-filter_complex` 硬绕过 tile grid**：`[0:v]` 会给出一块瓦片，
  「明确报错」变成「悄悄给错画面」，比原来更糟。
- 剩下的 ~0.9s 用户可感延迟不在 ffmpeg 上，而是 `scheduleRebuild()` 固定的
  250ms 去抖 + 合成重建 + AVPlayer 换 item。要再快就得动那条共享路径，
  那是另一件事（并且要先想清楚拖动时的连续重建）。
