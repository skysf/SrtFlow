# 2026-08-08 图片转静帧慢 20 倍：`-loop 1` 的输入帧率默认 25fps

## 症状

拖一张大图进 Video Edit 时间线，占位块要转好几秒甚至十几秒才变成真素材。
图越大越久，4K 图实测 **19.4 秒**。期间预览里那一段是黑的（占位块预览会跳过），
用户只看到一个转圈。

做「定格」功能时被逼着量了一次，才发现慢得离谱。

## 根因

`StillImageClipFactory.stillVideo` 的命令是：

```
ffmpeg -loop 1 -i x.png -t 60 -r 2 -vf scale=... -c:v libx264 ...
```

`-r 2` 是**输出**帧率，60 秒 × 2fps = 120 帧，这没问题。问题在输入：
`-loop 1` 走的是 image2 demuxer，它的**输入帧率默认 25fps**
（[FFmpeg 文档](https://ffmpeg.org/ffmpeg-formats.html#image2-1)）。于是
ffmpeg 老老实实把这张 PNG **解码了 25 × 60 = 1500 次**，再靠输出端的 `-r 2`
把其中 1380 帧丢掉。真正编码的只有 120 帧，1380 次解码是纯浪费。

一开始的怀疑是「编码器慢」，换 `h264_videotoolbox` 硬件编码测了一遍：
**20.5 秒**，几乎没变 —— 这一步直接把嫌疑从编码器身上摘掉，才转去看输入侧。

实测（本机 M1，`vendor/ffmpeg`，4K PNG）：

| 命令 | 输出 | 耗时 |
|---|---|---|
| 现状（4K 图 → 压到 1080p） | 120 帧 | **19.4s** |
| 改用 `h264_videotoolbox` 硬编 | 120 帧 | 20.5s（瓶颈**不在编码器**） |
| 加 `-framerate 2`（其余不变） | 120 帧 | **~1s** |
| 加 `-framerate 2` 且不缩放（4K 原尺寸） | 120 帧 | **2.2s** |

最后一行是关键：**修完之后，连原生 4K 都比修之前的 1080p 快 9 倍**。

## 修复

`Sources/SrtFlow/StillImageClipFactory.swift`：输入侧补一个 `-framerate 2`，
和输出的 `-r 2` 对齐。

```
-loop 1 -framerate 2 -i x.png -t 60 -r 2 ...
```

输出一帧不差、画质参数一个没动。缓存键还是从 `-v2` 升到了 `-v3`，但**不是因为
参数变了** —— 是要作废升级前可能留下的半成品（见下面第 2 条）。

同一次改动里还做了两件相关的事，各自的理由写在代码注释里：

1. **定格帧在真的会被缩时走「不缩放」政策**。照片路径的 1920×1080 上限
   **一个字没动** —— 抬全局上限会连带改变 Auto 画布尺寸
   （`VideoEditCompositionBuilder.renderSize` 取第一段素材的 `displaySize`），
   那是产品改动不是性能修复。政策的唯一判据是
   `needsNativeResolution(for:)`：尺寸没过上限时两条政策产出完全一样，
   统一走照片政策，好让政策能从 `info.displaySize` 唯一反推（缓存被清后
   要按原政策重转）。查缓存、重转、落地都必须带上政策，否则同一张 PNG 被
   定格段和普通图片段共用时会串线。
2. **临时文件 + 原子改名**，并把照片缓存键升到 `-v3` 作废升级前的旧文件。
   原来直接往最终路径写、只用 `fileExists` 判命中，转码被中断（切工程、退出
   App、磁盘满）会留下一个**永远命中**的半成品 mp4，之后这张图每次都解析到那段
   坏视频，且没有任何线索。搬运也不做「先查存在再搬」—— 那之间有 TOCTOU：
   同一张图的两个并发转换会同时通过检查，后搬的白白报错；改成直接搬、失败了再
   看目标在不在。

## 验证

- `scripts/check-project-file.sh`（120 项）—— 含新增的「定格帧重转要保住原生
  分辨率」回归：判据是存进工程文件的 `info.displaySize` 超过照片上限。
- 真实窗口：2560×1440 素材定格，检查器显示静帧就是 **2560×1440 · 1:00**，
  没有被压成 1080p；定格块 0.9 秒内出现。
- `swift run SrtFlowCoreChecks`、`scripts/check-preview-composition.sh`、
  `scripts/check-export-frame-rate.sh`、`checks/no-hardcoded-fps.sh` 全绿。

## 教训 / 防回归

- **ffmpeg 里凡是「循环一张图/一个源」的命令，输入帧率必须显式写死**，
  不能只设输出帧率。输入侧默认值和输出侧不一致时，中间那段差价是白烧的 CPU，
  而且完全不体现在输出文件上 —— 只看产物永远发现不了。
- **先证伪再优化**：换硬件编码器这一步花了两分钟，但它把「编码器慢」这个
  最直觉的假设当场排除，避免了往错误方向调半天参数。
- 静帧管线的分辨率政策是**两条**（照片 1080p / 定格原生），且缓存文件名分开。
  改这里前先读 `StillImageClipFactory` 里 `photoMaxWidth` 的注释，以及
  `VideoEditProjectIO.refreshStillClips` 里靠 `info.displaySize` 反推政策的那段
  —— 缓存被系统清掉后要按原政策重转，判据只有这一个。
