# 挂起主线程抓栈：挂起期间只做系统调用和裸读写

> 2026-10-06 起。`MainThreadStackCapture`（`Sources/SrtFlow/MainThreadStackCapture.swift`）从看门狗线程挂起主线程、
> 沿帧指针走栈；为什么要自己走栈、日志怎么读，见 [主线程卡顿日志](../testing/main-thread-stalls.md)。这一份只管
> **挂起期间**的硬约束。由来：[导出两次卡死](../bugfixes/2026-10-06-watchdog-capture-deadlocks-main-thread.md)。

## 一、约束

1. **挂起到恢复之间，挂起方只做系统调用和裸内存读写。** 系统调用只有 `thread_suspend` / `thread_get_state` /
   `thread_resume`；读写只碰挂起前分配好的缓冲区和主线程自己的栈。
2. **不分配，也不释放内存。** 主线程被挂起的那一刻可能正握着分配器的锁（xzone malloc 的慢路径、`mfm_alloc` 这类
   全局锁）。挂起方再要同一把锁，就永远等下去，主线程也永远不会被恢复：App 永久转彩球，只能强制退出。
   Swift 里会悄悄分配的写法都算：数组 / 字典 / 字符串的字面量和扩容、`map`、字符串插值、`print` / `Logger` /
   `os_log`、符号化（`dladdr` + demangle）、捕获可变量的逃逸闭包。
3. **不拿锁。** 同一个道理：`NSLock`、`os_unfair_lock`、dyld 和 Objective-C 运行时的锁、Swift 类型元数据缓存的锁，
   主线程都可能正握着。
4. **不碰要现场取类型元数据的类型。** 没优化的构建里，第一次碰一个导入的 C 结构（`arm_thread_state64_t`、
   `thread_basic_info`）或者没特化的泛型，要现场生成类型元数据：会加锁，会分配。所以寄存器按 `init` 里算好的
   字节偏移裸读，挂起期间不出现这个 C 结构类型。2026-10-06 写守卫时就撞上过一次：分配钩子的回调里用了
   `thread_basic_info`，取元数据要分配，分配又进回调，递归加锁当场崩掉。
5. **挂起和恢复只在 `walkWhileSuspended` 一处。** `capture()` 在挂起前分配好地址缓冲区和线程状态缓冲区，恢复
   之后才把地址拷成数组；符号化（`symbolicate`）在恢复之后做。往 `walkWhileSuspended` 里加任何一行之前，先对照
   上面四条。

## 二、为什么分配一次就能让 App 永远停住

- 看门狗在主线程卡过阈值（App 里 60 ms）时挂起它抓一次栈。卡得越多抓得越勤：2026-10-06 那台机器内存吃紧，
  导出一段 3 分半的片子时，每次进度更新都让主线程卡 100–300 ms，一分钟卡六七十到上百次，看门狗就挂起它这么多次。
- 内存吃紧时，主线程更常停在分配器里：页被换出去了要换回来，分配器走慢路径的时候也多。被挂起时它握着的锁，
  恰好是挂起方分配时要的那一把，就是死锁。压力实验取样看到的正是这样：主线程停在 `mfm_alloc` 里、挂起计数是 1，
  看门狗停在 `swift_allocObject → mfm_alloc → _os_unfair_lock_lock_slow`。
- 撞不撞得上，要看两条线程碰巧落在哪组核上：分配器的快路径不加锁，不共用同一组分配槽就碰不到同一把锁。原来的
  写法放进「主线程不停分配、另一条线程不停抓栈」的压力里，优化构建 10 轮里 5 轮在 1 秒内卡死，另外 5 轮一直不卡。
  所以守卫不靠撞，靠数（第三节）。
- 把锁握住再挂起，也做不成每次必现：主线程用 zone 的 `force_lock` 或 `_malloc_fork_prepare` 握住全部分配器的锁
  300 ms，优化构建里别的线程照样分配得出来（2026-10-06 探针）。

## 三、守卫

`scripts/check-main-thread-watchdog.sh`（`scripts/check-all.sh` 第 3 组）：

| 组 | 查什么 | 怎么判 |
| --- | --- | --- |
| 第 6 组（确定性） | 挂起期间抓栈线程分配 / 释放了几次 | 把 libmalloc 的 `malloc_logger` 钩子（MallocStackLogging / Instruments 记分配用的全局函数指针）临时指向自检的回调，抓栈线程每分配 / 释放一次就问内核主线程的挂起计数。300 次抓栈里挂起期间必须是 0 次；钩子找不到、或者一次分配都没看到，也红（不许空跑当通过） |
| 第 7 组（端到端） | 主线程不停分配时连续抓栈会不会卡死 | 主线程 2 秒里不停分配各种大小，另一条线程连续 `capture()`。判卡死的线程只用原子量、`write(2)` 和 `_exit`，抓栈计数 5 秒不涨就红；脚本另有 2 分钟的硬超时，免得 CI 挂到作业超时 |

第 6 组的回调自己也守第一节的规矩：缓冲区、偏移、线程号都在装钩子之前备好，回调里只做裸读写。

**反向验证（2026-10-06）**：

1. 换回原来的写法 → 第 6 组 3 次全红，每次 1500 次分配 / 释放落在挂起期间（300 次抓栈，每次 5 次）。
2. 在新写法的 `walkWhileSuspended` 里插一行一个元素的数组 → 第 6 组红，600 次。
3. 恢复修复 → 3 次全绿，挂起期间 0 次；挂起之外的分配照常有两千多次，说明钩子确实在数。

第 7 组在原写法上不是每次都红：没优化的自检构建里，原写法连跑 6 次只卡死 1 次。它是端到端的复现，不是主守卫。

## 四、人工回归

没有：第 6 组是确定性的。排查「App 卡死」时的提示写在 [主线程卡顿日志](../testing/main-thread-stalls.md) 第三节。
