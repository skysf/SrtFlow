# 滤镜（时间轴上的调色）

> 2026-09-21 产品决策 + 第一刀实现。改 `FilterLUT`、`FilterStack`、时间线的滤镜行、
> 导出滤镜链里的 `lut3d` 段之前必读。相关：[画面文字](text-overlays.md)（叠放次序）、
> [视频轨对等化](video-tracks.md)（行的上下顺序就是叠放次序）。

## 落点：滤镜是时间轴上的一段，不是片段的属性

用户拍的板（2026-09-21）：

| 决定 | 口径 |
| --- | --- |
| 是什么 | **时间轴上的一段**，不是贴在某个片段上的属性 |
| 染谁 | 这段时间里的**全部画面**（主轨 + 上层轨）；形状 / 文字 / 字幕**不染** |
| 叠加 | **允许**。顺序由 `FilterClip.layer` 定，**层号小的先作用** |
| 落点 | 从**播放头**开始，默认 3s，落在这段时间内**空着的最低层**；没有空层就往上开一层 |
| 替换 | 选中某一段时点卡片 = **只换种类**，时长/强度/层号都不动（同转场库的口径） |
| 强度 | 0–100，默认 100。0 = 原片，但**不自动删段** |
| 算不算总长 | **不算**。形状和文字自己就是画面，滤镜只是调色，染一段空白没有意义 |
| 时间线上能做什么 | 选中 / 拖动 / 两端裁切 / ⌫ 删除。**不支持分割**（切开两段同参数滤镜没有意义） |
| 三个开关 | 只吃**吸附**；磁吸和链接不管滤镜 |

滤镜行在时间线**最顶上**，26pt 的细行，有段才出现。它不参与「行的上下顺序就是
画面叠放次序」那套视频轨语义 —— 混进视频轨之间只会让人以为它是一条能放素材的轨。

## 层号进模型，不像文字那样现算

文字行的层号由重叠关系现算（`TextOverlayStacking`，纯显示用、不进模型）。
**滤镜不能这么做**：LUT 不可交换（先冷铁后褪色 ≠ 先褪色后冷铁），现算的层号会在
用户拖动别的段时重排，画面跟着变 —— 那是最难解释的一类错。

所以 `FilterClip.layer` 是持久字段，时间线上**下面的行先作用**。删掉某一层的最后
一段时 `compactFilterLayers()` 把空层收拢：收拢只改编号、不改谁先谁后，所以画面
不跳（有断言守着）。

**第一刀没有纵向拖动换层**（时间线现在只有剪辑能跨行拖）。想调顺序只能删了重加，
换层在第三刀。

## 地基：CoreImage 滤镜能不能染到视频画面

预览不走 AVFoundation 合成。那条路要自写 `AVVideoCompositing`，而现有的摆放 /
裁切 / 不透明度 / 关键帧全是 layer instruction 做的，自定义合成器会把它们整套推倒
重写 —— 轻量化优先（AGENTS.md 工程原则 1），所以选图层滤镜。

2026-09-21 用独立探针实测（纯红视频挂一张通道轮换 LUT，拍窗口取像素）：

| 挂法 | 结果 |
| --- | --- |
| `NSView.contentFilters` | ✅ 视频画面真的被染（红 → 绿）。**生产用这个** |
| `CALayer.filters` | ✅ 同样有效 |
| `CALayer.backgroundFilters` | ❌ **绝对不能用** —— 它染的是整个窗口的背景：同一窗口里**没挂任何滤镜**的播放器也被染了，挂了滤镜的那些还被染了两次 |
| `filters.<name>.inputCubeData` keypath 改参数 | ✅ 真的重绘（强度从 0 改到 1，取到的像素当场变绿） |

性能（1080p，33³ 的 LUT）：

| 模式 | 播放漂移 | 进程 CPU |
| --- | --- | --- |
| 不挂滤镜 | 0.150s | 3% |
| 挂一张 LUT | 0.157s | 3% |
| 挂着并 60Hz 改强度 | 0.156s | 6% |

漂移那 0.15s 是起播延迟，三种模式一致 —— 也就是**滤镜本身对播放零成本**（GPU 合成）。
按强度重算一张 33³ 的表实测 **0.109ms**，只占一帧预算的 1/150，所以不必退到 17³。

叠层（形状 / 文字 / 字幕 / 变换框）是 ZStack 里播放器**上面**的兄弟视图，天然不吃
滤镜 —— 和导出滤镜链里「滤镜插在画面合成之后、形状之前」一字不差。

## 强度：先插值表，再查表

一款滤镜就是一张 33³ 的表，由 `FilterRecipe` 的解析式算出来（不是外部 LUT 文件：
加一款只是加一行数据，App 体积也不涨）。强度是**恒等表与满强度表之间的线性插值**：

```
out = lerp(identity, LUT, s) 查表  ==  lerp(in, LUT(in), s)
```

两边严格相等（三线性插值对线性函数无误差，而恒等表在三线性下精确复原），所以
**强度不需要再额外做一次混合** —— 这条等式有断言守着（`checks/Filters/main.swift`）。

这也是为什么预览侧不去做「原图 ⊕ 满强度」的混合：`CALayer.filters` 是一条**线性链**，
链里拿不到未经处理的原图，混不了。重算一张表只要 0.109ms，拖滑块照样丝滑。

## 两条管线的对齐点

| | 预览 | 导出 |
| --- | --- | --- |
| 载体 | `CIColorCubeWithColorSpace` | ffmpeg `lut3d` |
| 数据 | `FilterLUT.cubeData(...)` | `FilterLUT.cubeFileText(...)` 写成 .cube |
| 顺序 | `FilterStack` 按 `orderedFilters` | 同一个 `orderedFilters` |
| 插值 | 三线性（CIColorCube 固定如此） | **必须显式 `interp=trilinear`**（默认是 tetrahedral） |
| 定义域 | `inputColorSpace` = BT.709 | **`format=gbrp` 垫在前面** |

四条硬约束，改任何一条之前想清楚另一边：

1. **顺序只有一份**（`TimelineState.orderedFilters`）。两条管线各排各的就是「预览一个
   味道、成片另一个味道」。
2. **`interp=trilinear` 必须显式写。** 不写就是 tetrahedral，和预览不是同一个算法。
3. **`format=gbrp` 必须垫在 lut3d 前面。** 不指定的话滤镜图自己协商像素格式，万一谈成
   YUV，这张 RGB 查找表会被当成对 Y/U/V 查表用，画面直接烂掉。
4. **预览必须用 `CIColorCubeWithColorSpace`，不是 `CIColorCube`。** 后者在 CI 的工作
   色彩空间（线性）里查表，而 ffmpeg 查的是伽马编码后的 RGB —— 同一份表喂给两边会
   得到明显不同的画面。

强度 0 的段**两边都整条跳过**（预览的 `FilterStack` 过滤掉、导出不进滤镜图）：那是
「先关掉看看」，成片应当和原片逐像素相同，而不是白跑一遍恒等表。

## 回归

- `scripts/check-filters.sh` —— LUT 数学、层号规则、**预览 vs 导出逐像素**（三方对齐：
  配方 ↔ CoreImage ↔ 真跑 ffmpeg）。反向验证做过：把 .cube 的通道顺序写反，逐像素
  那几条当场变红。
- `checks/ProjectFile/main.swift` 第 25 节 —— 存盘按需写键、往返保真、v17 登记、
  不认识的预设名要宽容回落。
- `scripts/check-filter-preview-attach.sh` —— **预览那条接线**：用生产的
  `FilterStack` + `FilterStackAttachment` 挂到真的 `AVPlayerView` 上，拍窗口数像素。
  上面那两条守的是「表对不对」，它对「表有没有真挂上去」一无所知 —— 接线断了
  那两条照样全绿，用户看到的却是毫无变化的预览。断言比的是**次序**
  （挂了 ≠ 没挂、60% 落在原片和 100% 之间、区间外等于原片、keypath 改强度真重绘），
  次序不受截图色彩管理影响。反向验证做过：把 keypath 那条便宜路改成空转，
  最后两条当场变红。**要图形会话，故意不在 `check-all.sh` 里**。

**自动化够不着的（改动后按 [GUI 冒烟流程](../testing/gui-smoke-testing.md) 实机过一遍）：**

1. 拖滤镜块的手感：吸附亮线、边缘自动滚动、同层挡住不许重叠、跨层能叠。
2. 拖强度滑块时画面是否跟手（丝滑度本身没法断言，只能看）。
3. 滤镜行的出现/消失：加第一段时长出来、删最后一段时收回去。
4. 播放中跨过滤镜段的起止点，画面切换是否干净（时钟 0.05s 一跳，边界误差上限 50ms）。
