# 写代码的规范：模块化与单文件体积

> 2026-09-24 用户定的规范，原话：「代码要模块化，方便后期维护，一个代码文件里面不要太多行」。
> 适用于仓库里的全部代码：`Sources/` 下的 App 与核心库，`checks/`、`scripts/` 下的检查和
> 工具（Swift / shell / Python），测试也算。行数上限由 `checks/source-file-size.sh` 钉住；
> 其余几条守卫够不着，写的人和审的人按第五节的清单过一遍。

## 一、为什么

- **文件越大越没人敢动。** 时间线视图拆分前是一个 2101 行的文件，拆成一族文件
  （`VideoEditTimeline*.swift`，分工写在 `VideoEditTimelineView.swift` 顶部）之后才重新
  改得动。
- **改之前要先读完。** 每个代理、每次会话都得先把文件读进来：几百行能一次读完、看清全貌；
  两千行的文件只能读片段，改一处漏一处。
- **自检是按文件编的。** 每个检查脚本自己列一份 swiftc 源文件清单。一个文件混着模型和视图，
  只想测模型的检查也会被视图的依赖拖下水（[源文件清单守卫只盯着枢纽文件](../bugfixes/2026-09-21-source-list-guard-only-watched-the-hub.md)
  第三条教训）。模块切得干净，自检才编得动、测得准。

## 二、单文件行数（守卫钉着）

| 规矩 | 口径 |
| --- | --- |
| 目标 | **≤ 400 行**。超过就该想想哪一块职责能单独拿出去 |
| 上限 | **600 行**，超过就红 |
| 算哪些 | `.swift` / `.sh` / `.py`，含测试、检查脚本和还没提交的新文件 |
| 怎么数 | `wc -l`，空行和注释都算 |
| 老文件 | 2026-09-24 就已经超过 600 行的 26 个，登记在 `checks/source-file-size-baseline.txt`，**行数只许降不许涨** |

**超了就拆，不许删注释、把几行挤成一行来凑数。** 这个仓库的注释是约束的一部分（「为什么
只能这样做」），删掉它换来的行数是假的。

老文件的三条：

1. **往里加代码，就在同一次改动里从它身上拆出至少等量的行。** 新代码本来就该进新文件；
   非改老文件不可时，把它身上职责独立的一块顺手搬出去抵账。
2. **变短了就跑 `checks/source-file-size.sh --update` 把基线改小**，降到 600 以内那一行会被
   自动删掉。不改小的话天花板还在老位置，文件能悄悄长回去 —— 所以守卫对「变短了但基线没改」
   也判红（同 [预览性能 ratchet](preview-perf-ratchet.md) 的「进步必须登记」）。
3. **`--update` 只会改小或删行**：不会替新的超标文件登记，也不会替长了的文件抬线。老文件改名
   时手改基线里那一行的路径，审查时看得见。

顺手拆可以，**不要借题做一次性大重构**：拆出来的那块要职责独立、有自己的名字，一次改动
只搬它。

## 三、怎么拆：模块化的六条

1. **一个文件只管一件事。** 文件名说出这件事；文件开头一段注释写清它管什么、不管什么、
   和谁配合（参考 `VideoEditTimelineView.swift` 顶部的分工表）。新类型、新功能默认开新文件。
2. **优先抽出有名字的顶层类型，别给大对象继续加方法。** 纯值 `struct`、当命名空间用的
   `enum`、小的 `final class`：接口窄、依赖少。
   - `VideoEditProject`、`TimelineState`、`EditClip` 已经很大。新功能的规则写成独立类型
     （现成的例子：`AudioGain`、`FadeWindow`、`VolumeCurveLayout`、`CompositionAudioTracks`），
     大对象身上只留一两行转交。
   - **别开「只有 extension」的文件**：自检清单守卫认不出这种文件（没有类型名可匹配），
     漏编了要到 CI 才红（`checks/check-script-source-lists.sh` 开头）。要拆就连同一个顶层
     类型一起拆。视图拆块时，把那一块写成它自己的 `struct …: View`，body 第一行照样计数
     （写完跑 `checks/preview-perf-wiring.sh --fix`，见 [预览性能 ratchet](preview-perf-ratchet.md)）。
3. **纯计算和副作用分开。** 几何、时间换算、增益表、落点这类规则写成纯函数 / 纯值，自检能
   直接编、直接测；视图只做展示和回调（`onLive` / `onCommit`）；AVFoundation、ffmpeg、文件
   读写集中在少数几个适配层里。
4. **同一条规则只有一处实现。** 两条管线、两个入口用同一条规则时，都调同一个函数，不许各写
   一份（dB 换算只有 `AudioGain`，渐变夹紧只有 `FadeWindow.clamped`）。仓库里不少 bug
   案例都是「同一件事算了两份，后来分叉了」（比如
   [转场预览有、成片没有](../bugfixes/2026-09-20-transition-preview-export-divergence.md)）。
5. **复用优先，抽象克制。** 同一模式出现第二次才抽成共享组件；没有真实的第二个用例，不提前
   造泛型和框架（AGENTS.md 工程原则 2）。
6. **函数也别太长。** 一个函数超过约 60 行，就按步骤拆成几个有名字的小函数；SwiftUI 的
   `body` 太长就拆子视图。

## 四、守卫

`checks/source-file-size.sh`（`scripts/check-all.sh` 第 1 组）：

| 情况 | 结果 |
| --- | --- |
| 没登记的文件超过 600 行（含新文件） | 红：按职责拆 |
| 基线里的老文件长了 | 红：新代码进新文件，或同一次改动里拆出等量的行 |
| 老文件变短了、基线没改小 / 降到 600 以内还挂着 / 文件已经不在了 | 红：跑 `--update`（改名就手改路径） |
| 一个文件都没扫到 | 红：扫空 = 假绿 |

原来钉在 `checks/timeline-drag-wiring.sh` 第 0 节的「时间线这一族单文件 ≤ 800 行」并进了这条
守卫（全仓一个上限，不留两份账）；那一节现在只管「这一族的文件都在」。

**反向验证（2026-09-24）**：

1. 新建一个 601 行的未提交文件 → 红，点名这个文件；此时跑 `--update` → 拒绝，基线原样不动。
2. 给基线里的 `checks/timeline-drag-wiring.sh` 追加一行 → 红（「多了 1 行」）。
3. 删掉它一行、不改基线 → 红；跑 `--update` 后基线变成新行数、转绿。
4. 往基线里加一个只有 425 行的文件和一个不存在的文件 → 两条都红。

全部恢复后转绿。

## 五、审查清单（守卫够不着的）

- [ ] 新文件开头写了它管什么、不管什么？
- [ ] 新规则是独立的类型 / 纯函数，还是又堆进了大对象？
- [ ] 有没有同一条规则写了第二份？
- [ ] 超过 60 行的函数能不能按步骤拆？
- [ ] 往老的超标文件里加了东西的话，同一次改动里拆掉了等量的行吗？
