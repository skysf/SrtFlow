# 画面文字（text overlays）

> 2026-09-17 产品决策 + 三刀实现；2026-09-18 加入对焦动画。改 `TextRenderer`、`TextTypesetter`、
> 导出滤镜的文字段、或预览的文字叠层之前必读。

## 落点：文字是标注，不是轨道上的一段

用户拍的板：文字是**浮在画面之上的标注**，和形状同一族；不是视频轨上的一段。

代价说在前面：文字**不能被上层轨的画面盖住**，也不能跟着某一段视频一起磁吸
搬家。换来的是文字可以自带一整套逐帧动画，不必和剪辑的关键帧动画争"谁覆盖谁"
——那个语义讲不清楚。

叠放次序固定为：

```
剪辑 → 形状 → 文字 → 字幕
```

**预览的 ZStack 和导出的滤镜链必须一字不差地按这个顺序。**文字压在形状之上是
产品口径，不是实现顺手：用户要能"画一个半透明色块当底板、文字放上面"。

## 唯一的绘制入口

**预览和导出只准从 `TextRenderer.render` 出画面。**两边唯一的差别是传进去的
`canvas` 尺寸。

字幕那边是反面教材：导出走 libass、预览用 SwiftUI 八份阴影凑个假描边，文件里
自己写着「这是近似效果」。字幕能忍是因为样式就那么几档；文字要精调质感，预览
对不上就等于没法调。

连带的两条：

- **预览按物理像素渲染**：画布尺寸是点，Retina 上一点两个像素。按点渲染再让
  SwiftUI 放大，文字糊掉一档 —— 而"预览里调得准"就是这个功能的全部意义。
  渲染尺寸乘 `displayScale`，显示时用 `Image(decorative:scale:)` 折回点。
- **落点取整**：`TextRenderer` 把位图落点 `.rounded()` 到整像素，ffmpeg 的
  `overlay` 也按整像素贴。不取整的话两条管线差半个像素，逐点比对的回归永远红。

## 尺寸都以 1080p 为基准

字号、描边宽度、投影偏移/模糊、底板圆角与内边距，全部按 **1080p 画布**定义，
渲染时乘 `canvas.height / 1080`（与字幕的 `PlayResY` 同一个口径）。

按高度换算，不是按宽度：按宽度算的话，同一套样式在 16:9 和 9:16 之间切换时
字号会突变。

## 版面框 = 定位框

文字块的定位框是**版面框**（宽 = 用户设的折行宽度，高 = 排出来的总高），
不是字的墨迹范围。左对齐的一行短字会靠在框左边，而不是被拉回正中 ——
改对齐方式时文字在一个固定的框里移动。

位图只有**包络**那么大（版面框 + 描边 + 投影 + 底板，再按角度转一圈的外接框），
不是整幅画布。整幅 1080p RGBA 是每帧 8MB，包络通常只有几十分之一；
第二刀逐帧导出时这个差别是几百 MB 和几 MB。

## 绘制顺序

```
底板 → （投影 ⨁ 描边 ⨁ 填充）
```

括号里三样收在**一个透明层**里（`beginTransparencyLayer`），投影设在层外面 ——
于是整块字（含描边）投出**一个**影子。不这么做的话描边和填充各投一个，边上是
一圈脏边。

底板**在层外面，不参与投影**：底板自己是实心块，再投一个影子只会让深色底板
边上糊一圈更深的东西。需要底板带影子就用形状标注垫一层。

描边走**两倍线宽**再被填充盖掉内半边，露在外面正好是用户设的宽度。直接用
`.fillStroke` 的话线宽跨在字形轮廓上，一半吃进字里，细字体会被啃掉一圈。

渐变填充用 `setTextDrawingMode(.clip)` 把裁剪区收成字的形状，再往里刷渐变。

## 坐标系（最容易写错的地方）

排版和渲染全程 **y 轴向上**（Core Graphics 原生），不像 `ShapePNGRenderer`
那样翻成左上原点 —— 文字要喂给 `CTFontDrawGlyphs`，每翻一次就多一处符号
写反的机会。

对外只有 `RenderedText.origin` 是左上原点（画布像素），因为调用方（SwiftUI
叠层、ffmpeg overlay）都按左上原点摆图。

## 文字的字体表和字幕**不是同一份**

字幕的 `FontCatalog` 只收「文件可读 + CoreText 能解析」的字体，因为烧字幕要把
字体文件软链进任务目录喂给 libass；macOS 的苹方等系统中文字体放在普通进程读
不了的目录里，libass 打不开会悄悄换字体。

文字没有这个约束 —— 渲染全程走 Core Text，字体由系统字体服务提供。用字幕那份
表的话，苹方这种最常用的中文字体会从列表里消失，而它明明画得出来。所以另有
`TextFontCatalogStore`（`CTFontManagerCopyAvailableFontFamilyNames`）。

## 时间线上的行（2026-09-24 用户拍板：行号进模型）

`TextOverlay.row`：0 = 最下面那条文字行（紧挨形状行），越大越靠上。**行序就是画面上的
叠放序**：行号大的画在上面，同一行按数组顺序；预览叠层（`visibleTextOverlays`）和导出
（`VideoEditExportGraph`）都按 `TimelineState.textOverlaysInStackingOrder` 这一份序 —— 准确地说都读它去掉
藏起来的（V，2026-09-26）之后的 `renderedTextOverlays`，藏起来的文字照样占着自己那一行
（[段的显隐](clip-visibility.md)）。
规矩都在 `VideoEditTextRows.swift`：

| 事 | 规矩 |
| --- | --- |
| 新加文字 / 数字 | 永远在最上面**新开一行**（`row = textRowCount`）：新字压在所有旧字之上 |
| 上下拖 | 指针落在哪一行就去哪一行；那一行在这段时间被占了就**往上找第一条空行**；比最上面那一行还高 = 顶上新开一行；文字行以下 = 留在原行（`TextRows.dropTarget` 判、`settleTextRow` 落，和横向位移同一次 `perform`） |
| 横向拖 | 落点在自己那一行被占了，同样往上找空行（文字自己没有障碍，不会被挡住不许动） |
| 删 / 换行之后 | 空行收拢（`compactTextRows`）：只改编号不改上下，画面不跳 |
| 存盘 | `row` 无条件落盘，有文字就是 **v21** 数据（旧版丢了行号，重叠的字按时间重排、谁压谁就变了） |
| 老工程 | 没有 `row` 键：载入时 `normalizeTextRows` 按当年的自动排布补（`TextOverlayStacking` 只剩这一个用途；当年贪心层 0 就画在最下面那条文字行，行号照抄，屏幕上一行不挪）；个别缺的当 0；负数收口 |
| 形状 | 不动：还是一行，允许重叠 |

「同一行不重叠」是**落点**的规矩，不是硬约束：裁切把两段拉到相交时照样各画各的。

以前的做法（2026-09-24 之前）：层号按时间重叠现算、不存盘。问题是现算的层号会在拖别的段
时重排，而画面上谁压谁跟着变 —— 用户没法把某段字固定压在另一段上面。

文字块用**固定的中性色**（`TrackPalette.textBlock`），不跟轨道色表走：文字不是
一条轨，给它一个轨道色会让人以为时间线上多了条视频轨。

## 动画

三个槽：**入场、出场、强调**，再加一个全局**强度**。没有更多旋钮 —— 质感来自
缓动曲线、逐字错峰间隔、回弹幅度这些用户调不出来的东西，摊开只会让人调出难看
的结果还以为是功能不行。

| 效果 | 怎么实现的 |
| --- | --- |
| 淡入淡出 | 整层 alpha |
| 上浮 | 整块位移 + 淡变。**入场从下方来，出场继续向上走** —— 连贯的一段运动比"原路退回去"更像设计过的 |
| 弹性缩放 | 入场 `easeOutBack`（冲过头约 1.1 再回弹），出场 `easeInCubic` 直接收走 —— 出场再弹一下像没关紧的弹簧 |
| 打字机 | 逐字**硬切**。半透明的字在打字机里看起来像渲染出错，不像"正在打出来" |
| 逐字错峰上浮 | 逐字淡变 + 位移，第 i 个在 `i/(n-1) × (1-0.45)` 处起步，各自用 45% 的时长走完 —— 于是最后一个正好在进度 1 到位 |
| 模糊解析 | 整层 alpha + `CIGaussianBlur`，**不带缩放** |
| 对焦 | 一边缓缓放大、一边从模糊收清，两件事同时发生。见下面单独一节 |
| 遮罩擦除 | 横向裁剪区。**线性**，不加缓动 —— 擦除的进度本来就是几何量，加了会让扫过的速度忽快忽慢 |
| 描边生长 | 描边先按擦除扫出来（快 1.4 倍），填充过了 35% 再化进来 |
| 呼吸（强调） | 整段期间 `sin` 缩放，与入场/出场**相乘**叠加 |

### 对焦：和 `pop` / `blur` 都不一样的第三种

用户要的是「缓慢地从小变大 + 从模糊变清晰，两件事一起」。现有两种都不是：
`pop` 带回弹（观感是"弹进来然后停住"），`blur` 只糊不缩放。

三个决定：

**一、曲线接近匀速**（`easeInOutSine`），**不用**别的入场统一用的
`easeOutCubic`。后者把动作压在前三分之一 —— 那是"弹进来"，正好是"缓慢"的
反面。回归里那条「中点必须落在两端正中」就是钉这个的：easeOutCubic 的中点
在 0.875，会当场红。

**二、出场继续放大**，不是缩回去 —— 像镜头一直往前推，最后失焦。和 `rise`
的「入场从下面来、出场往上走」同一个思路：连贯的一段运动。代价是包络要按
放大后的尺寸留余量，所以 `envelopeAllowance` 里**只看出场那一侧**是不是
对焦 —— 一律按放大算的话，只做入场对焦的文字会白白多出一圈空位图。

**三、起手不透明度可调**（`focusStartOpacity`，默认 0.35）。两头是两种观感：
1 = 纯相机对焦（一上来是一片满不透明的模糊色块再收紧成字），
0 = 从全透明淡进来（衔接柔和但没了对焦味）。入场和出场**对称**用同一个值，
想要干净地消失就调到 0。这是唯一一个「只对某一种效果有意义」的旋钮，
所以界面上只在真选了对焦时才露出来。

### 两条硬约束

**一、动画是相对基准位置的偏移。** 画面上拖出来的位置永远是动画播完的落点，
动画不改 `centerX/centerY`。否则动画一跑选中框就跟着飞，根本拖不住。

**二、时刻必须先钉到工程帧的网格上**（`TextAnimator.quantize`）。预览和导出
都从它进 —— 不量化的话预览停在两帧之间、成片停在帧上，逐点比对永远差一点，
而"预览所见 = 成片所得"是这整套东西的前提。

### 时长夹紧与声音、画面渐变共用一份

「入场 0.6s + 出场 0.6s 撞上只有 0.8s 的文字」和「音频渐入渐出超过段长」是同
一个问题，所以用同一个 `FadeWindow.clamped`：各自不超过段长，两者之和超了就
按比例同时收。存的是**用户的意图**，夹紧在读侧做 —— 段被拉长之后动画应当跟着
恢复，而不是写入那一刻就被当时的时长永久截短。

夹紧还保证了入场和出场**不会重叠**，于是求值是干净的三段式（入场 / 中间 /
出场），不用考虑两种效果同时作用时怎么合成。

### 检查器：离散写入 vs 连续写入

**下拉、开关、数值框的打字与步进箭头一律走 `perform`，只有滑块和横向拖动走
live。**

理由是 `liveApply` 的语义：它每次都从**手势开始时的那份快照**重新应用一次
完整修改。滑块有「松手」信号（`labelledSlider` / `onEditingChanged` 会调
`endLiveEdit` 把快照收掉），离散控件没有 —— 快照会一直挂着，下一次写入就从
那份陈旧状态出发，把上一次的改动一起抹掉。

2026-09-17 的现场：入场选了 Fade（快照里还是 None），再点秒数的步进箭头，
Fade 当场退回 None；同一个错误也让「勾了粗体再拖字号」掉粗体。

约定用**命名**承载：体内做 live 写入的绑定工厂一律叫 `liveXxx`，而且这个名字
要一路带到转发的参数上（`liveSeconds:`）。光看控件那一端是不够的 —— 绑定常常
先转发成一个普通名字的参数，到了 `Picker` 那里就看不出是 live 的了，
而那正是漏掉那次的形态。守卫见 `checks/inspector-live-binding-wiring.sh`。

### 导出：只逐帧渲动画进行中的那段

一段 5 秒的标题，入场 0.6s + 出场 0.6s，中间 3.8 秒画面**一帧都没变** ——
那 3.8 秒渲成一张图 + 一个时间区间就够了。30fps 下是 37 帧 vs 150 帧。

三种片段，三种接法：

| 片段 | ffmpeg |
| --- | --- |
| 静止 | `-loop 1 -t <总长> -i text0-mid.png`，与形状同款 |
| 一次性序列 | `-itsoffset <起点> -framerate <fps> -i text0-in_%05d.png`，帧与时间线精确对齐（实测） |
| 循环 | `-framerate <fps> -i …`，再 `loop=loop=-1:size=N,setpts=N/fps/TB+起点/TB` |

序列末尾**多渲一帧**：序列的最后一帧落在 `end - 1/fps`，而 `enable` 一直开到
`end`；那之间的输出帧会撞上输入流的 EOF，`eof_action=pass` 当场把文字整个撤掉
—— 动画最后一帧闪一下没了。多一帧就把这个缝堵上了。

**循环动画只渲一个周期。** 呼吸是周期性的，整段逐帧渲会随文字时长线性膨胀 ——
10 分钟的呼吸文字能写出几个 GB，把磁盘撑爆。所以中间那段只渲一个周期，交给
`loop` 滤镜铺满。为此周期必须是**整数帧**（`TextAnimation.breathePeriod(frameRate:)`
按帧率取整），否则循环接缝处相位会错开，看起来像卡了一下。

### 包络按整段动画的极值算

每一帧都按**同一个**框渲，overlay 的 x/y 才能是常数。按当帧算的话尺寸每帧都
变，贴图位置得跟着改，动画会抖。

外扩量来自 `TextAnimator.envelopeAllowance`：上浮/逐字的最大位移、模糊的
1.5 倍余量、弹性缩放冲过头的 1.1 倍、呼吸的幅度。留小了的症状不是报错，
而是**动画被位图边缘切掉一条直边** —— 回归里那条"逐帧确认最外圈全透明"专治它。

### 逐字动画为什么要拆成一个字形一次绘制

每个字形的不透明度和位移都不一样，整行批量喂位置做不到。代价是绘制调用多了
N 倍，但标题就几十个字，而且**只在动画进行中**才走这条路（`perGlyph == nil`
时仍是整行批量）。

渐变填充遇上逐字更麻烦：「所有字形一起进裁剪区、刷一次渐变」不成立了，只能
一个字形一次裁剪一次刷。但渐变的几何仍按**整块墨迹**算 —— 于是每个字形拿到
的是它在整块渐变里本该有的那一段颜色，而不是各自从头到尾渐变一遍。

## 选中框的三种把手，三种数学

框本身是转过的，把手位置也是转过的，而拖动位移在屏幕坐标系里。每种把手各挑
一条显式算法，不用通用仿射解算器 —— 那种写法在角度接近 90° 时数值会炸。

| 把手 | 算法 |
| --- | --- |
| 移动 | 位移直接加到中心上。与旋转无关 |
| 角把手 | 位移**反旋转**回本地坐标，量「把手到中心」这条向量变长了多少倍。等比 —— 文字的缩放只有字号一个自由度 |
| 边把手 | 同样反旋转，只取 x 分量改折行宽度。框是中心锚定的，拖一边两边一起长，所以乘 2 |
| 旋转 | 指针相对框中心的极角减去起手时的极角。⇧ 吸 15° |

把手一律用**命名坐标系**（`TextFrameBox.space`），不是 `.local`（随把手自己
移动，位移被自己抵消）也不是 `.global`（拿不到画布原点，旋转算不出极角）。

起手状态必须冻结：`frame` 在手势过程中会变（改了字号框就大了），所有算法都拿
起手时的尺寸当基准 —— 用当前帧当基准的话，缩放会自己加速成指数。

**把手的可点范围必须写在 `.offset` 之前。** `.offset` / `.rotationEffect` /
`.scaleEffect` 只挪画面、不挪布局框；写在它们后面的 `.contentShape` 按的是没挪过的
框。2026-09-24 旋转把手就是这么写的：画出来的黄点在框上方，可点的圆留在框正中 ——
文字正中心有一个看不见的旋转区，想拖字一按下去就变成旋转，黄点本身反倒点不动
（[案例](../bugfixes/2026-09-24-text-rotate-handle-hit-area-at-center.md)）。
守卫 `checks/hit-shape-before-offset.sh` 扫全部源码，不止这一个文件。

## 预览上点得着哪里

2026-09-24 起（用户反馈「几段字挤在一起时点不准」）。可点范围由 `TextHitGeometry`
一次排版算出来，`TextOverlayCanvas` 只管摆：

| 情况 | 可点范围 |
| --- | --- |
| 没选中 | **看得见的那一块**：墨迹四周外扩 6pt；开着底板时连整块底板（底板按版面框画，不按墨迹） |
| 选中的那段 | 另垫一块**整个版面框**，框里的空白处也能拖 —— 垫在所有字的可点范围**下面** |
| 空文字（刚 Add 出来） | 整个版面框，否则什么都点不着 |

为什么不按整框判：版面框的宽是折行宽度，默认占画面 80%，「090」这么短的数字也是
80% 宽，几段字的框互相盖着，点在「° SOUTH」的字上会选中旁边的数字。选中那段的整框
垫在下面，是为了「点在别的字上还是选别的字」，不被这块大框抢走。

范围一律按**定版串**算（同选中框）：数字滚动时位数会变，按当帧算的话可点范围会跳。
投影和模糊不算进去 —— 那会让可点区域比看得见的字大出一大圈。

## 没有迁移，但按需抬版本

工程格式：文字本身是 **v11**（`requiresFormatVersion11 = !textOverlays.isEmpty`），
文字动画是 **v12**（`requiresFormatVersion12 = 有文字带非空动画`），
数字元件是 **v13**，对焦动画是 **v14**，数字的等待（`NumberRoll.delay`）是 **v21**（按需：0 不落键）。

按需，不是无条件：`TimelineState.encode` 里空数组不落盘，两处必须一致 ——
不一致的话，一份从没用过文字的工程会莫名其妙地打不开于旧版。

带文字就必须抬：只认 v10 的旧版不认识 `textOverlays` 这个键，打开带文字的工程，
画面上的字**当场消失**，随手一编辑触发自动保存就永久没了。带动画同理 ——
只认 v11 的旧版会把文字变成**硬切出现**，而入场那一下正是标题最显眼的地方。

## 数字元件

`TextOverlay.number` 非 nil 时内容**由它算**，`text` 不再显示。做成一个可选
字段而不是另一个模型 —— 于是数字白捡整套样式、动画、摆放和时间线能力，
「数字」只是内容的来源不同。两种形态：

| 形态 | 做法 |
| --- | --- |
| 数值递增 | 每一帧重新格式化插值后的数值，字符串真的在换 |
| 老虎机 | 排版**定版**，只改每一位的轮位；带上同时露着两个数字，当前那个往上移出去、下一个从底下补进来。位数不同的两头见下面「位数不同的两头」 |

### 等待：先停在起始值上，再开始滚（2026-09-24 用户拍板）

`NumberRoll.delay`（检查器里叫「Delay / 等待」）从**这段文字的起点**算：前 `delay` 秒进度
为 0、显示起始值（老虎机的每一位停在起始值的那一位上），之后照常滚 `duration` 秒。
`settleTime = delay + duration` 是数字停下来的时刻，导出切段的头部按它算（下面「导出」一节）。
0 = 没有等待，不落盘；用了才是 v21 数据。

### 格式化不跟系统区域走

千分位一律逗号、小数点一律句点。看起来武断，但**成片是文件**：同一份工程在
不同区域设置的机器上必须渲出一模一样的画面。要别的写法用前缀/后缀兜。

各位上的数字从**格式化之后的串**里取，不从数值上除 —— 除法在小数位上会踩
浮点误差（`12.5 / 0.1` 可能是 124.999…，第一位小数会算成 4 而不是 5），
而串就是用户看到的东西，天然对得上。

### 位数不同的两头：首帧就是 from、末帧就是 to（2026-09-25）

定版串按位数多的那一头排（包络、选中框、可点范围都按它，滚动中不跳）。位数少的那一头，多出来的
高位**本来就不存在** —— 以前那几格照样画成 0：`365 → 90` 停在「090」，`0 → 4827` 起步是「0000」，
千分位逗号和负号也照样留着（[案例](../bugfixes/2026-09-25-odometer-leading-zero.md)）。
规矩都在 `NumberOdometer`（`VideoEditTextOdometer.swift`，纯值）和 `TextTypesetter.layout(widths:)`：

| 事 | 规矩 |
| --- | --- |
| 不存在的那一位 | 数字带在那一头是**一格空白**：365 → 90 的百位滚 3 → 2 → 1 → 空。两头恰好是同一格（行程为 0：`100 → 5` 的十位）就往滚动方向多走一格，不然空白和数字挤在同一格上 |
| 宽度 | 滚向空白的那一格，宽度跟着收（离空白格还差几成就占几成宽）；排版在属性串上按比例收掉它的步进，前缀和负号贴过来 |
| 谁不动 | **居中和右对齐右边不动**（个位那一轮一动不动），左对齐左边不动（`placeCollapsing`） |
| 正在收的那一位 | 字形留在自己原来那一格里滚走 / 滚进，不跟着收窄的步进挪 |
| 千分位逗号 | 跟着它左边（高一位）那一位一起滚走 / 滚进 |
| 负号 | 只在一头有时自己滚进滚出，节奏排在最高位之上 |
| 定版串 | 位数取多的那头、任一头是负数就带负号；位槽只从去掉前后缀的那一段认 |

**居中为什么不左右各让一半：**数字后面紧跟单位是最常见的摆法（「90°」「365 天」「100%」），单位
常常是另一段字。居中重新摆的话，数字一挪中间就空出半格 —— 第一版就是这样修的，自检全绿，拿
用户南极那条片子一渲，「90」和「° SOUTH」之间空出了半格。代价：居中的数字**位数变少**之后（倒数），
停下来的数不在拖放的中心，而是右边贴着原来的位置（就是以前「090」里 90 的位置，只是少了那个 0）。
要落定之后正好居中，用「数值递增」（每帧按真实的串排）。

**正在收的那一位为什么留在原地：**它的步进收窄了，Core Text 会把它排到挪过之后的位置上。跟着挪的话，
居中时只剩上半截的「1」蹭到「3」跟前，看着像个逗号（第一版的第二个毛病）。

以前的两个连带错（同一次修掉）：定版串取的是「两个完整显示串里字符多的那个」，两头符号不同时漏位
（`-12 → 345` 取了「-12」，终点画成「-45」）；位槽是整串扫的，后缀里的「2」（「m2」）被当成个位、
前缀里的「.」（「No.」）被当成小数点。

### 老虎机不是真实里程表

真实机械里程表的公式是「第 k 位的轮位 = 值 / 10^k」，很漂亮，但**终点不收口**：
4827 的千位会停在 4.827，也就是卡在 4 和 5 中间糊成一片。现实中高位只在低位
归零时才对齐，而目标值一般不是整十整百。

所以每条带子是从**起始数字**转到**终止数字**，中间多转几圈：

- 圈数**取整**，否则起点显示的数字不等于起始值的那一位；
- 圈数按 `|to-from| / 10^(k+1)` 算并封顶三圈 —— 不封顶的话 `0 → 1000000`
  的个位要转十万圈，30fps 下每帧跳过几万个数字，画面是一团糊；
- 高位**提前收口**（`lead`），这就是老虎机依次锁定的那个节奏。

### 等宽数字是自己排的，不是字体特性

第一版走 `kNumberSpacingType` / `kMonospacedNumbersSelector`。实测
（2026-09-17）：**苹方根本没实现这个特性**，请求是空操作 —— 它的数字是比例的
（100pt 下 `1` 是 40、`8` 是 60），一跳数整行宽度就变 20pt，居中的标题会左右晃。

而 Helvetica / Arial 这些**本来就等宽**，特性生效没生效根本看不出来 ——
这个坑极容易被「在我机器上是好的」盖过去。

所以等宽自己排：按最宽的数字定**格距**，在属性串上逐个数字加 kern 把它撑成
一格，再把字形挪到格子正中。在属性串上做而不是排完版再挪，是因为这样行宽、
折行、对齐全都自动算对；排完再挪只能挪字形，整行的宽度还是错的。

老虎机的带子用**同一份**格距（`TextTypesetter.digitMetrics`），否则数字带和
它的格子对不齐。

### 两份排版

数字滚动时「这一帧」和「定版」的字符串可能不同（数值递增会换串，位数还会变），
所以渲染里有两份排版：

- **定版**（`settledText` = 前后缀 + 位数取 `from` / `to` 里多的那个、任一头负就带负号）：定位、包络、
  选中框全按它算。按当帧算的话位图尺寸每帧都不一样，贴图位置就固定不住了。
- **这一帧**：真要画的内容。

行数不同时（位数变多折了一行）要把**第一行基线**对到定版的第一行上 ——
不对齐的话，多出一行的那一刻数字会整个竖着跳。

### 导出：头部逐帧要算上滚动窗口

`animatedHead = max(入场时长, 等待 + 滚动时长)`。数字滚完之前画面每一帧都在变，
哪怕入场动画早就结束了 —— 只按入场时长切段的话，滚动的后半截会被冻成一张
静止图，数字数到一半卡住。等待也要算进去：只按滚动时长切的话，数字会在等待结束
那一刻被冻住（`scripts/check-text-render.sh` 第 16 组真跑导出数帧钉着）。

头和尾加起来可能超过整段（滚动比入场长时），要夹一下，否则两段在时间上重叠，
同一刻贴两张图，文字会明显变浓。

## 还没做的

1. **样式预设库**：一键套用「字体 + 颜色 + 描边 + 动画」的组合，结构照抄
   `BurnInStyle` 的 `isBuiltIn` + 内置预设列表。
2. **毛玻璃底板**：好看但代价是文字层要知道底下那一帧长什么样 —— 导出要在
   ffmpeg 里抠一块区域模糊再贴回去，预览也要另走一条路。用户当前口径是不做。
3. **发光 / 抖动**：真辉光要加模糊卷积，成本比其余效果跳一档，暂缓。
4. **数字换行**：位数变多折行时数字会被拆成两行，看起来是坏的。基线已经对齐
   （不会跳），但产品上更该是「数字不折行」。
