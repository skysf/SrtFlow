# 预览性能 ratchet：数「做了多少件活」，只许降

CI 上起真 App，按固定场景数预览做了多少件活，和 `checks/PreviewPerf/baseline.json`
比：**多了就红，少了必须把新数写进基线**。基线只会往下走。

本文只写**长期约束**；目标、拍过的板和探针实测见
[预览性能 ratchet 方案](../plans/2026-09-24-preview-perf-ratchet.md)。

## 一、量的是活，不是 CPU

GitHub 托管的 macOS runner 是虚拟机（`VirtualMac2,1`，3 核），2026-09-24 探针实测：

1. **读不到 CPU 指令计数器**：`proc_pid_rusage` 的指令数、周期数、能耗三台全是 0。
   本机 M1 读得到，但 CI 不用自托管 runner（用户拍板）。
2. **CPU 时间在 runner 之间差到两倍**：同一份 1080p 解码 + 合成，三台的中位数约
   670 / 400 / 310 ms。拿它卡 CI 必然时红时绿。
3. **数活是精确的**：200 次数据变化，三台上 SwiftUI 都恰好重算 200 次，开不开窗口都一样。

所以卡的是整数：哪个视图的 body 被重算了几次、`updateNSView` 被调了几次、Canvas 画了
几次、合成重建了几次、开了几次素材、换了几次播放条目、建了几个电平表 tap。GPU 和解码
那一侧用合成指令里的代理数字（下面第四节）。CPU 时间照样记，写在 CI 的汇总页上，**只报不卡**。

## 二、计数必须接满

`PerfCounters`（`Sources/SrtFlow/PerfCounters.swift`）只有设了 `SRTFLOW_BENCH_OUT`
才记账，平时每个埋点只读一个静态布尔值。埋点的规矩：

1. **每个** SwiftUI 视图和修饰器的 body 第一行是 `let _ = PerfCounters.body(Self.self)`；
   每个 `NSViewRepresentable.updateNSView` 第一行是 `PerfCounters.update(Self.self)`；
   每个 Canvas 的绘制闭包第一行是 `PerfCounters.canvas(Self.self)`。
2. body 写成标准形式（`var body: some View {` 独占一行）。写成一行的话扫描守卫看不见它。
3. 视图不许重名：计数按类型名记账，重名就串成一笔。

`updateNSView` 不能省：反向验证时给按钮加 `.id(clock.time)`（每跳重建一次），body 次数
纹丝不动（它本来就每跳重算），多出来的全在提示包着的 AppKit 视图的 `updateNSView` 上。

漏插一个，那个视图每跳一下都在重算，账上也看不见，ratchet 就成了摆设。三条都由
`checks/preview-perf-wiring.sh` 钉着（在 check-all 第 1 组）。规则按「全部视图」定，不管
它在不在编辑器里 —— 比按「编辑器里的视图」定好守，共用组件的退步也看得见（首跑最大的大头
就是共用的即时提示修饰器）。

**不用手写那一行**：新写视图后跑 `checks/preview-perf-wiring.sh --fix`，漏插的计数自动补在
开头行下面（守卫红的时候也会提示这条命令）。它只补标准写法 —— body 开头独占一行、
`updateNSView` 的签名在同一行、`Canvas { … in` 写在同一行；别的写法不去猜（猜错了会把计数
插进参数列表里，编都编不过），照样判红，改成标准写法再跑。只改已有视图的 body 内容什么都不用加。

非视图的埋点（`PerfCounters.Event`）只挂在代价实打实的地方：时钟每跳一下
（`PlayerClock.observePlaybackTime`）、换播放条目、建合成、建合成时开素材（2026-09-25 起素材走
进程级缓存 `MediaAssetCache`，只有真开了文件才记；同一个文件第二次重建记 0）、新建电平表
tap、audioMix 快路径。守卫也钉着这几处。

## 三、测试怎么跑

`scripts/check-preview-perf.sh`（CI 第 1 组里单独一步，**不在 check-all.sh 里**：要图形
会话，基线也按 runner 的环境记）：

1. 用固定参数的软件编码现生成素材（`vendor/ffmpeg`，三段 1080p 主轨、一段 720p 上层
   视频、20 秒背景音乐、一份字幕）。**音频统一 48kHz 立体声 AAC**：一条合成音轨中途
   换源格式，电平表的 tap 会死掉（[推子与电平表](audio-mixer.md)第三节第 7 条）。
2. 起 debug 版 App（数的是活，和编译优化无关；第 1 组已经编好了），
   `-mainWindowSection videoEdit` 直接进编辑器。App 里的 `PreviewBench`：
   - 窗口钉成 960×600，贴着屏幕可用区域的左下角摆，并激活 App（Canvas 只画看得见的部分，
     窗口大小会改数）。**尺寸必须放得进可用区域**：CI 的屏幕是 1024×768，去掉菜单栏和程序坞
     放不下 720 高，系统会在之后某个时刻把窗口挤回去；
   - 空闲和时钟连跳这两段**量的过程中窗口或 App 的状态一变**（移动、改尺寸、key、激活、
     屏幕参数 —— 监听通知，变了又变回去也算），这一段作废重量，最多 3 次，重量了几次写在
     报告里。那种变化会让检查器、时间线整个重新布局一遍（2026-09-24 实测：检查器多重算 33 次、
     时间线缩放比例被改两次），数就不是这段代码的了；
   - 用和界面按钮同一批入口搭场景（`PreviewBenchScenario`：`basic` 一段主轨素材；
     `busy` 三段主轨带转场、上层视频缩小半透明带入场动画、背景音乐带渐入和音量曲线、
     字幕、文字、形状、滤镜、选中一段素材）；
   - 等预览落定（不在重建、不在导入、播放条目就绪、计数连续一段时间没动），依次量：
     **空闲 3 秒**、**时钟连跳 60 下**（走真播放同一个入口 `observePlaybackTime`）、
     **改几刀**（改音量走快路径、挪上层视频 / 改转场时长 / 变速要重建、改文字只动叠层）、
     **合成负载**、**真播放 3 秒**（跳几下由真实时间定，只报不卡）；
   - **「落定」要等后台的媒体读取读完**（`PerfCounters.backgroundReadsInFlight` 归零：时间线
     缩略图的取图、波形的解码，开始和结束都登记了，守卫钉着）。光看界面计数「一段时间没动」
     不够：后台解码时界面一下都不动，解完才更新一次 —— 首跑里「空闲 3 秒」冒出过一次缩略图
     重画。以后加新的后台读取（会在读完时通知界面的那种），照这两处登记起止；
   - **时钟连跳每跳一下都要等界面完全停下来，才跳下一下，不能按固定间隔跳。** 有些重绘
     跟着屏幕刷新走，一跳的更新拖过了下一跳，两跳就并成一次刷新，数随机器快慢变
     （2026-09-24 首跑：按 50ms 固定间隔跳，CI 上一跳要吃约 58ms CPU，两遍标尺重算
     55 / 59 次）；
   - 「改几刀」本身是一串异步的事（防抖、建合成、换条目、seek），中间刷几次屏看时机，
     所以这一段**只卡事件计数**（建合成、开素材、换条目、建 tap、快路径），body /
     Canvas 次数只报；
   - 写 JSON，直接 `exit`（未命名工程正常退出会弹「要不要保存」）。
3. 每个场景跑两遍（两遍不一样再跑第三遍），交给 `checks/PreviewPerf/compare.swift` 判。

## 四、GPU 和解码：数合成指令里的活

预览的合成交给系统合成器在 GPU 上做，它的 GPU 时间不记在我们进程头上（探针：按进程
统计的 GPU 时间读出来是 0），虚拟机也读不到能耗。`PreviewBenchComposition` 从交给系统的
那份合成指令里数：

- `video.layerFrames`：每一帧合成几层，全片加总（一层 = 一路解码 + 一次混合）；
- `video.megapixelFrames`：每一帧每一层实际落在画布上的像素，全片加总；
- `filters.frames`：每一帧挂几层滤镜，全片加总；
- `video.compositionTracks`：合成里有几条视频轨。

透明度、变换、裁切都按合成器的规则逐帧线性插值。这几个数只能靠**不做看不见的活**降
（被整个盖住的层、全透明的段、强度为 0 的滤镜）——**不许拿画质换数字**（用户拍板），
按预览区尺寸降分辨率、给时钟降频这类都不算优化。

## 五、比对规则

1. **要有两遍一模一样。** 每个场景先跑两遍；不一样就跑第三遍，用一模一样的那两遍，
   另一遍当受了干扰扔掉（汇总页上照写，出局得多了看得见）。三遍两两都不一样，说明有东西
   在异步地落地、测试本身不稳 —— 修测试，不许放宽基线绕过去。首跑就靠这条抓到了
   「按固定间隔跳」「后台缩略图没读完」「窗口被系统挤动」三个问题（上一节）。
   允许出局一遍，是因为 CI 虚拟机上偶尔有窗口和 App 都没发通知的系统事件，让几个视图
   多更新一轮（约十遍一次，只多不少），那不是这段代码的活 —— 它的认法和两遍都撞上时的
   处理见下面第六节。
2. **计数逐项相等。** 多了是退步；少了是进步，但**必须在同一个 PR 里写进基线**，不然这次
   省下来的，下一个 PR 可以悄悄花回去。多出来的项要登记，消失的项要删。
3. **内存峰值按容差比**（`memoryTolerance` = 10%：探针里 runner 之间差 2–5%，首跑同一台
   runner 上两遍也差了 4%）：超上限算退步，降得多只提示。
4. **基线只许降。** 比的是合并提交第一个父提交里的基线（所以 checkout 要 `fetch-depth: 2`）。
   任何一项被改大了，这个 PR 就**不许动产品代码**（`Sources/` 下除 `PreviewBench*.swift`
   以外的文件）。要加开销，得先在别处省回同样多（用户拍板）。

比对器红了会打印两份基线：「改好的基线」（进步、新增、删除都写进去了，退步的项保留旧值）
给改代码的 PR 用；「全部实测值」给重定基线的 PR 用。CI 的汇总页有逐项对比、CPU 时间和
「时钟跳 60 下每个视图重算了几次」的明细；结果和 App 日志作为附件 `preview-perf` 上传。

## 六、已知的偶发误报

CI 虚拟机上偶尔有一个**不发任何窗口 / App 通知**的系统事件，让检查器的数值框（连带上面的
即时提示）和时间线的缩放桥接 `TimelineMagnificationBridge` 多更新一轮，大约十遍一次。
它落在空闲、时钟连跳哪一段都有可能。按 2026-09-24 的基线，见过的有：busy 的 `ticks.body`
+99、`ticks.update` +35；basic 的 `ticks.update` +2、`idle.update` +1（basic 没选中东西，
检查器里没有数值框，只剩缩放桥接那一两下）。

- 只有一遍撞上：被「要有两遍一模一样」挡掉，汇总页上多一行「当受干扰的那遍扔掉」。
- 两遍都撞上：它每次多出来的活一模一样，两遍会「一致」地多，**被报成退步**。

**怎么认、怎么办**：一个没动编辑器界面的 PR 在性能这一步红了，而且汇总页明细里多出来的正好
是上面这几个视图 —— 在 PR 的 Checks 页点「Re-run failed jobs」重跑。重跑还红，就是真的退步。
以后优化改变了这几个视图每跳的次数，多出来的数会跟着变：**认的是哪几个视图，不是具体数字**。

查到一半的线索在 PR #68（已关；分支 2026-09-25 删了，代码还在 PR 页面上，要接着查就在那儿点 Restore branch）：在每一段里监听**全部**通知（`NotificationCenter`
和 `DistributedNotificationCenter`、`queue: nil`）会让 App 第一遍就段错误。下次先收窄监听
（只听具名的通知，或者放到主队列上），再拿撞上的那遍和干净的那遍比，找出是哪个事件，然后
像窗口变化那样「量到一半撞上就重量」。

## 七、什么时候可以重定基线（数字往上走）

只有两种，都**单独开 PR、不碰产品代码**：

- **runner 的镜像换了**（macOS / Xcode 版本变了，SwiftUI 的内部行为可能跟着变）。汇总页
  会同时打出基线记的环境和这台 runner 的环境。
- **测试场景改了**（改 `PreviewBench*.swift`：加场景、加阶段、加计数项）。

两种都用比对器打印的「全部实测值」整份替换 `baseline.json`。

## 八、已知盲区

- 数的是「件数」，不是「每件多贵」：一次重算一个小图标和一次重算整条时间线记一样的数。
  所以**明细里挑大头**：汇总页按次数排序列出了每个视图。
- 真正的解码时间、GPU 时间、WindowServer 里的合成、AVPlayer 内部的活都看不见，只有第四节
  那几个代理数字。
- 真播放那一段只报不卡：跳几下取决于 runner 的快慢。
- 只量了两个场景。没进场景的功能（比如定格、关键帧、录屏导入）退步了它也不会知道 ——
  加功能时顺手把它放进 `busy`（按第七节单独开 PR 重定基线）。

## 九、时间线上的块：不读工程、按值比较

时间线上一列列的东西（剪辑块、文字块、形状块、滤镜块、字幕 cue 块、音量线、标尺、转场卡片）
**不许读工程的属性**（工程是 `@Observable`，body 里读了哪个属性就订阅了哪个；2026-09-25 以前的写法是
`@ObservedObject var project`，订阅整个工程），**必须按值比较**：

1. 块只收算好的值。要读工程里的什么，由读工程的那一层（时间线的每一行）算好传进来
   （剪辑块用 `ClipBlockContext`：轨道色、推子、当前工具、帧率；选中与否是 `isSelected`）。`project`
   可以传，只拿来**调动作**（选中、切、标记、菜单）。手势回调里要现读最新值的那几处（音量线起手时
   现读那一段），行尾写「手势里现读」—— 那不在 body 里，不订阅，守卫认这个记号。
2. 块自己写 `struct X: View, Equatable` 并实现 `==`，只比画面用得到的输入。闭包不比：它们
   捕获的是时间线视图，读的是它的 `@State` 和工程对象，永远是最新的。
3. 构造处套 `.equatable()`。**不套等于没做**：输入里有闭包，SwiftUI 比不出「没变」，时间线每
   重算一次（拖动每动一下）全部块都跟着重算。

为什么：那时 `VideoEditProject` 是一个大 `ObservableObject`，任何一个 `@Published` 一动全体订阅者
重算。列表项订阅它，就是「点选一段（只改 `selection`）→ 73 个块全部重算、61 条音量线全部
重画」（2026-09-24 用户工程实测，案例
[时间线上每个块都订阅着整个工程](../bugfixes/2026-09-24-timeline-blocks-observe-whole-project.md)）。
换成 `@Observable` 之后同一个坑换了个样子：块的 body 里读一下 `project.selectedClipIDs`，点选一段照样
全部块重算（第十三节）。

守卫：`checks/preview-perf-wiring.sh`「时间线上的块」一节，钉着八个视图的三条（Equatable；块的
struct 里不读工程的属性 —— 调方法、写入、`clock` / `meters`、标了「手势里现读」的放行；构造处紧跟
`.equatable()`）。盲区：在 body 里**调**工程的方法，一样会订阅方法里读到的属性。新加一种块，往那张表里加一行。

拖动位移那一半 2026-09-25 也做了：会话搬进 `TimelineDragBox`，时间线持有不订阅、块只收自己那份，
拖动每一拍时间线 body 不再重算（[拖动手势](timeline-drag-gestures.md) §0b，案例
[拖动会话住在时间线的 @State 里](../bugfixes/2026-09-25-drag-session-in-timeline-state.md)）。
还留着的：整轨换位（§5i）每一拍仍重算整条时间线。

## 十、只有一个小视图关心的状态，不放在工程上发

（这一节写于工程还是 `ObservableObject` 的时候：那时工程上每发一次 `objectWillChange`，订阅工程的整个
编辑器 —— 提示修饰器、轨道头、工具栏、检查器、转场库 —— 就重算一轮，debug 版一轮 150–400 ms。换成
`@Observable` 之后，写一个属性只叫醒 body 里读了它的视图，道理见第十三节；下面几条的做法照样成立。）

- **只有一个小视图关心的状态，放进只有它订阅的小 `ObservableObject`**，工程持有它（`let`，不是
  `@Published`）；工程里要用这个值的逻辑直接读。例：「预览正在重建」→ `PreviewRebuildStatus`，
  只有工具栏的 `PreviewRebuildSpinner` 订阅（2026-09-25，案例
  [松手重建把每个素材重新打开一遍](../bugfixes/2026-09-25-rebuild-reopens-every-asset.md)）。
- **不许给该驱动界面的属性加 `@ObservationIgnored` 了事**（以前的说法是「不许把 `@Published` 摘掉」）：
  视图读一个不通知的值，界面只在碰巧别的东西刷新时才对。加之前先 grep 谁在 body 里读。
- **没变不写**：以前 `@Published` 值一样也发。现在工程上能比较（`Equatable`）的属性写同样的值不通知
  （Swift 6.2 起宏展开里带比较，本机 6.3 实测）；不能比较的类型照旧写一次通知一次，这一条对它们还得自己守。
- 守卫：`checks/preview-perf-wiring.sh`「预览正在重建」那一节（工程上不许有发通知的重建开关、工具栏用
  `PreviewRebuildSpinner`、别的视图不许直接读值）。

以前记着的同类：自动保存成功时写 `hasUnsavedChanges = false`，每次都是整个编辑器一轮 —— 换 Observation 之后
body 里读它的只剩工程名下拉那一个视图，不再是问题。（重建收尾时时钟
无条件写 `peekTime` / `hasVideo` / `time` 那一条，2026-09-25 起根视图不订阅时钟，只剩第十二节名单里
那几个小视图各算一遍。）

## 十一、点一下选中一段，时间花在哪（2026-09-25 实测）

量法：南极工程（77 段）、1180×860、进程内冒烟驱动在主轨两段之间来回点选 8 次，看进程 CPU
（步骤表和每次改动的对照都在当天会话的 scratchpad 里，数字抄在这儿）。

- **debug 和 release 几乎一样**：每点一下 204 ms 对 196 ms（拖一段音频 30 拍 768–802 对 746–753 ms）。
  `sample` 看主线程：忙的时间里约 78% 在 SwiftUI / AttributeGraph / AppKit 自己身上（整棵树 diff、
  更新、布局），我们自己的 body 代码只占约 22%。**所以省时间靠少让视图失效，不靠把 body 写快。**
- 逐块拿掉量出来的份额（每点一下 204 ms 为基准）：

  | 拿掉的 | 每点一下 | 省下 |
  | --- | --- | --- |
  | 提示修饰器（`instantHelp` 变空操作） | 190 ms | 约 7%（body 次数却少了 53%：它多但便宜） |
  | 转场库那一栏 | 184 ms | 约 10% |
  | 检查器 | 144 ms | 约 30% |
  | 三样全拿掉 | 113 ms | 剩下的是时间线本体、轨道头、工具栏、预览上的叠层、根视图 |

  检查器和转场库的活大半是**该做的**：换了一段，检查器每个数都得换；转场卡片的小样用的是选中那条缝
  两边的画面。body 次数不是代价的好代理 —— 提示修饰器占了一半的 body，只占 7% 的时间。
- **时间线每点一下重算两遍**：一遍是它自己订阅的工程变了（`_project changed`），一遍是根视图
  `VideoEditView` 也订阅着工程、重算时新建了时间线这个结构体（`@self changed`，60–140 ms 之后）。
- **别给 `VideoEditTimelineView` 套 `.equatable()` 去省第二遍**（换 Observation 之前）：实测块的选中高亮**只在第二遍里更新**。
  时间线自己那一遍里 body 读到的已经是新选择，可 `ForEach(rows)` 被判成没变（`rows` 相等、闭包捕获的
  是同一个 `self`），里面的块一个都没重算 —— 省掉第二遍，点了哪段都不亮（模型里选中了，所以读
  `state` 的冒烟核对照样全绿，只有看截图才发现）。拖动的成员名单（`dragMembers`，时间线的 `@State`）
  不受影响：拖一段已经选中的块，块照样跟手（同一天实测）。守卫：`checks/preview-perf-wiring.sh` 最后一节。
  检查器、素材库那一栏也有同样的第二遍（套 `.equatable()` 每点一下再省约 12 ms），截图上检查器换段是对的，
  但里面每一块有没有同样的依赖没逐项核过，没做。
- **换成 `@Observable` 之后（第十三节），这两遍都没了**：点一下根视图和时间线本体的 body 一次都不跑，
  块照样拿到新的选中 —— 读选择的那一处在 `ForEach` 的内容里，Observation 把它算在那一项头上、直接叫醒它
  （实测每点一下 `ClipBlockView` 2 次：新选中的和刚取消的，截图上高亮跟过去）。上面那条「别套
  `.equatable()`」的理由随之不成立；守卫还钉着，是因为套了之后改动时高亮、位置、缩放跟不跟得上没人验过。

往下走的方向：用户拍板把工程换成 Swift 的 Observation（2026-09-25，「A 做了」），做完的样子和实测见第十三节。

## 十二、播放头的每一跳只叫醒跟着它动的东西（2026-09-25）

播放器时钟 `PlayerClock` 播放时一秒发二十次，订阅它的视图一秒重算二十遍。2026-09-25 之前根视图、时间线
本体、检查器、素材库那一栏、字幕列表都订阅着它，一跳约 172 次 body，播放卡
（[案例](../bugfixes/2026-09-25-playback-wakes-whole-editor.md)，拍过的板见
[播放丝滑方案](../plans/2026-09-25-smooth-playback.md)）。规矩：

1. **订阅时钟的只许是真跟着播放头变、又足够小的视图，按类型名单管**：时间线的播放头竖线 + 影子指针 +
   跟随滚动（`TimelinePlayheadLines`）、标尺上的把手（`TimelinePlayheadHandle`）、预览的播放器画面
   （此刻的调色，`PreviewPlayerSurface`）、预览上的字幕 / 文字 / 形状 / 变换框、电平表、按钮可用性的小修饰器。
   根视图、时间线本体、标尺本身、检查器、素材库那一栏、字幕列表都**持有不订阅**（`let clock`），body 里
   读到的是现值、重算时机由别的东西给。烧字幕页那三个用的是另一个时钟，没量过，先在名单里。
2. **大视图里只有一小块要跟着时钟** → 把那一小块拆成它自己的视图去订阅（`VideoEditPlayheadFollowers.swift`
   里的几块就是这么从根视图拆出来的），不要让大视图订阅。
3. **只关心「变没变」** → 小视图里 `onReceive` 自己那一份，变了才写 `@State`：播放键只看播放状态，时间读数
   只看显示的那一格（十分之一秒），字幕列表只看换没换句。按钮能不能点看播放头的 → `.disabled(followingPlayhead:)`：
   只有那个小修饰器订阅时钟、算一个布尔，判据闭包现读工程和 `clock.time`。
4. **停着时才有意义** → 读播放头的慢读法 `PacedPlayhead`（`clock.whilePaused` / `clock.atRest`）：只跟播放头被
   **放**到哪儿走（`PlayerClock.placed`：seek、换片、卸片），播放中一次不发，停下来追上一次，不认悬停。检查器读
   `whilePaused`（停着时拖播放头找关键帧照样实时）；素材库那一栏读 `atRest`（拖播放头的过程中也不换，松手刷一次）。
   **慢读法不许订阅时间回调**（`clock.$time`）：播放把它带着走的每一跳都会叫醒检查器和素材库。
5. **播放中点素材库的转场卡片**，作用在面板显示的那条缝上（`applyTransitionFromLibrary(_:at:)` 传面板用的那个时刻），
   不是播放头此刻最近的那条 —— 看到哪条改哪条。

守卫：`checks/preview-perf-wiring.sh`「播放器时钟只许跟着播放头动的小视图订阅」（类型名单、检查器和素材库接对了
节奏、慢读法不订阅时间回调）；慢读法的行为由 `scripts/check-player-clock.sh` 的自检钉着。

性能测试的「时钟连跳」是在播放器**停着**时调 `observePlaybackTime`：慢读法只认放置、不认时间回调，所以测试里检查器和
素材库同样不被叫醒，数和真播放一致。要是改成「按播没播判断」，测试会一直当成停着，数就和真播放对不上了。

实测：CI 的 busy 场景时钟跳 60 下，body 10313 → 1109、AppKit 控件更新 1081 → 1（basic 3000 → 870）；进程内冒烟
（用户的南极工程，真播放 3 秒 55 跳）一跳约 25 次 body，一半是电平表，根视图、时间线本体、检查器、素材库、
工具栏图标、数值框一次都不重算。

## 十三、工程是 `@Observable`：读了什么，就只被什么叫醒（2026-09-25）

第十一节那条「往下走的方向」用户拍了板（「A 做了」）：`VideoEditProject` 从 `ObservableObject` 换成 Swift 的
Observation。以前工程上任何一个 `@Published` 一写，33 个 `@ObservedObject var project` 的视图连同子树全部重算；
现在视图 body 里读了哪个属性，就只在**那个属性**变时重算。案例和实测见
[点一下选中一段，整个编辑器跟着重算](../bugfixes/2026-09-26-selection-wakes-whole-editor.md)。规矩：

1. **驱动界面的存储属性不加标注（被观察），不驱动界面的一律 `@ObservationIgnored`**：后台任务、缓存、代号、
   书签、连续修改的快照、`undoManager`、`isDraggingVolume` 这类。被观察的清单和以前的 `@Published` 一模一样
   （19 个），`let` 的（时钟、电平表、`rebuildStatus`）本来就不观察、各有自己的订阅规矩。新加一个被观察的属性，
   同步加进冒烟的计数清单 `SmokeProjectChanges.watched`（冒烟起手时拿 `Mirror` 核对，漏了直接报错）。
2. **按属性叫醒，不按值**：`selection` 是一整个结构，改了剪辑的选中，只读 `transitionSeamID` 的视图也会被叫醒；
   `state` 是一整个结构，改任何一处，读 `state` 的视图全都重算。所以**大视图（根视图、时间线本体、检查器、
   素材库）的 body 读什么要克制**：只为一两个按钮读的东西，拆成小视图去读 —— 垃圾桶和「分离声音」就是这么从
   根视图里拆出来的（`SelectionToolbarButtons`，`VideoEditToolbarStateButtons.swift`）。
3. **只有 body 里的读算数**：按钮动作、手势回调、`onChange` 的动作闭包里读不订阅（`onChange(of:)` 盯的那个值
   是在 body 里读的，照样订阅）。绑定（`$project.x`，用 `@Bindable`）的 getter 在控件自己更新时才读，算在控件头上，
   不叫醒建绑定的那个视图。`ForEach` 的内容闭包里读的，算在那一项头上（实测）：点选一段时时间线本体的 body
   一次不跑，块照样拿到新的选中（第十一节那个坑随之消失）。反过来，body 里**调**工程的方法，方法里读到的属性
   照样订阅。
4. **不可观察的东西没人顺带刷新了**：以前工程一变整个编辑器重算，读 `NSUndoManager`、`RecentProjects`、
   `@ObservationIgnored` 属性的视图被顺手带着刷新；现在不会。读这种东西的视图要自己找叫醒它的来源：显式读一个
   跟着变的被观察属性（「文件 ▸ 最近打开」读 `documentURL`，反向验证：去掉就一直停在启动时的「没有」），或者听
   它自己的通知（撤销 / 重做听撤销栈的「一组关上了 / 撤销了 / 重做了」三个通知，外加读 `state` 管换工程清栈；
   **别听 `NSUndoManagerCheckpoint`**，`canRedo` 自己就会发它，听了就是死循环）。
5. **值没变的写入不通知**（能比较的类型；Swift 6.2 起宏展开里带比较，本机 6.3 实测），但 `didSet` 照样每次都跑。
   不能比较的类型写一次通知一次，第十节「没变不写」对它们还得自己守。
6. **冒烟看 `event:project.changed.<属性>`**：两次快照之间哪个属性变了几轮（同一拍里写几次算一轮）。点选一段
   只该有 `selection`；多出别的属性，就是有东西在白白叫醒读它的视图。

实测（南极工程，1180×860，进程内冒烟在主轨两段之间来回点 8 次，main 1f3f693 和这一版交替各跑三遍）：

| | main | 换 Observation 之后 |
| --- | --- | --- |
| 进程 CPU（8 次，三遍） | 1548 / 1494 / 1519 ms | 1155 / 1118 / 1109 ms（约 −26%） |
| 每点一下 body 次数 | 334 | 120（−64%） |
| 主线程忙（采样 24 次点选里的同一段窗口） | 1973 ms | 1467 ms（−26%），其中 SwiftUI 更新那一块 1113 → 655 |

每点一下根视图、时间线本体、轨道头的每一行、推子、工具栏图标、行高把手、工程名下拉、文件菜单**一次都不重算**；
还在算的是换一段本来就要换的：检查器（新那段的每个数）、素材库那一栏（新那条缝的小样，2 遍：接缝一变一遍、
两张帧取齐一遍）、预览上的选中框、高亮变了的那两个块。

**剩下的大头不在我们的 body 里**：主线程忙的时间里约一半是 SwiftUI 在按下 / 松开时做命中测试
（`ViewResponder.hitTest` 顺着整棵响应树找，`HoverResponder` / `GestureResponder` 一层层 `containsGlobalPoints`），
它只和响应树有多大、多深有关，和重算几个视图无关 —— 换 Observation 前后纹丝不动（596 对 653）。想再往下，
方向是让不接事件的东西不进响应树（块内装饰 `.allowsHitTesting(false)` 这类），没做、没验证。

CI 的性能测试不量点选（只卡空闲 / 时钟连跳 / 事件计数），这一轮省下的它看不见。想锁住，按第七节另开一个**只改
`PreviewBench`** 的 PR 加一段「点选」（比如 busy 场景里换选中几次，数每个视图重算了几次）。
